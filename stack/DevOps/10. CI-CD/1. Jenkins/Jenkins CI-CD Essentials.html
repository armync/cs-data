Continuous Integration and Delivery with Jenkins

Introduction to CI and CD

Continuous Integration (CI) automatically builds, tests, and validates code each time a change is pushed. Continuous Delivery/Deployment (CD) takes validated artifacts and promotes them through environments, ultimately releasing to users in a controlled and repeatable way.

In simple terms, CI answers the question “Is the code in the main branch working and testable right now?” and CD answers “Can we move that working code into production safely?”

If You Are New to CI/CD

Before going deeper, here are a few basic terms you will see often:

  • Repository (repo): Where your source code lives (for example, on GitHub, GitLab, or Bitbucket).
  • Commit: A saved change in your repository history.
  • Branch: A separate line of development. Many teams use a main branch and short-lived feature branches.
  • Build: The step that compiles/transforms your source code into something that can be executed or deployed (for example, a JAR file or a container image).
  • Test: Automated checks that verify the code behaves as expected.
  • Artifact: The built output of your application (for example, a JAR, a Docker image, a ZIP with static files).
  • Environment: A place where your application runs (development, test, staging, production, and so on).
  • Pipeline: A sequence of automated steps (build, test, package, deploy) defined as code.
  • Agent: A machine (physical, virtual, or container) where Jenkins runs the build steps.

If these concepts are new, it is enough to understand them at a high level. You do not need to know every detail to start using Jenkins.

Why CI?

Catch issues early, reduce integration pain, keep the main branch in a deployable state, and avoid “it works on my machine” situations.

Why CD?

Ship smaller changes more frequently, reduce release risk, and create a predictable release rhythm.

Essentials

Version control, automated tests, build artifacts, pipelines, environments, observability, and a clear promotion flow.

Mindset

Everything-as-code, immutable artifacts, fast feedback, trunk-based development, feature flags, and continuous learning from failures.

AspectContinuous IntegrationContinuous Delivery / Deployment
TriggerEvery change (push/PR)Manual or automated promotion
OutcomeValidated build + test resultsDeployed artifact in target env
FeedbackMinutesMinutes–hours with approvals
Risk controlTests, code quality gatesRollouts, flags, progressive delivery
Rule of thumb: CI answers “are we broken?” as quickly as possible; CD answers “can we release now?” safely and repeatably.

Automation with Pipelines

A pipeline is the automated workflow that starts from a code change and ends with a validated artifact (and possibly a deployment). It is the backbone of CI/CD.

Beginner note: You can think of a pipeline like a checklist that the system follows every time someone pushes code: pull the code, build it, run tests, and optionally deploy it.
1

Source & Branching

Use trunk-based development with short-lived branches. Protect main and require reviews plus CI checks. Avoid long-lived feature branches that drift from the actual production code.

2

Build

Produce reproducible builds. Embed metadata (commit SHA, build time, build number) into artifacts so you can always answer “what is running in production?”.

3

Test

Start with unit tests and add integration and end-to-end tests over time. Run tests in parallel whenever possible. Publish JUnit/XML and coverage reports for visibility.

4

Quality & Security

Static analysis (SAST), dependency scanning (SCA), secret scanning, container image scanning, and SBOM generation. Fail early when risk is detected.

5

Package & Registry

Publish versioned artifacts to a registry (for example, Maven, npm, Docker). Use immutable tags or digests so that the same artifact is deployed to every environment.

6

Deploy

Automate deployment to non-production first. Use infrastructure as code (Terraform, Helm, Kustomize). Promote with approvals and change windows as needed; avoid rebuilding the same artifact for each environment.

7

Observe & Rollback

Use telemetry (logs, metrics, traces), SLOs, health checks, and dashboards. Provide fast, tested rollback or roll-forward strategies.

Tip: Keep pipelines fast (ideally under 10–15 minutes) by caching dependencies, splitting tests, and using elastic agents. Slow feedback reduces developer productivity.

Core CI/CD Concepts

  • Pipeline as Code: Store pipeline definitions (for example, a Jenkinsfile) in the same repository as your application.
  • Shift Left: Run quality and security checks as early as possible in the pipeline.
  • Fail Fast: Stop the pipeline quickly when critical checks fail, instead of running later stages unnecessarily.
  • Idempotent Deployments: Running the same deployment step multiple times should lead to the same target state.

Deployment Strategies

Deployment strategies define how new versions of your application are rolled out to users. The appropriate choice depends on risk tolerance, traffic patterns, and infrastructure.

Recreate

Stop the old version and then start the new one. Simple to understand but causes downtime. Suitable for internal tools or maintenance windows.

Rolling

Replace instances gradually. Minimizes disruption and is common in Kubernetes. Works well when instances are stateless.

Blue-Green

Run two identical environments (“blue” is live, “green” is new). Switch traffic via routing or DNS; rollback is as simple as switching back.

Canary

Release to a small percentage of users first, then expand if the deployment is healthy. Combine with metrics and alerts for automatic promotion or rollback.

Shadow

Mirror real traffic to the new version without user impact and compare responses and performance before rollout.

Feature Flags

Decouple deployment from release. Toggle exposure, run A/B tests, and roll back instantly without redeploying.

Practical pattern: Use rolling deployments by default, canary or blue-green for high-risk changes, and feature flags for user-visible functionality.

Jenkins: Introduction

Jenkins is a flexible automation server with a large plugin ecosystem. In a modern setup, Jenkins configuration, pipelines, and infrastructure should be treated as code.

Pre-Requisites for Getting Started with Jenkins

To follow the examples in this document, it helps to have:

  • A basic understanding of Git (clone, commit, push).
  • Access to a Git repository hosting service (for example, GitHub, GitLab, or Bitbucket).
  • A machine or VM where you can run Docker (for example, a local development machine).
  • For the Java examples, a JDK and Maven or Gradle project.

You can start on a local machine for learning and later move the same concepts to a shared Jenkins controller used by your team.

  • Key plugins: Pipeline, Git, Credentials Binding, Timestamper, Kubernetes, Docker, JUnit, JaCoCo, OWASP Dependency-Check, Pipeline Utility Steps (among others).
  • Naming: The term agent replaces the legacy term slave. The older term may still appear in some user interfaces or documentation.
Best practice: Keep Jenkins itself as “thin” as possible. Offload heavy builds to agents, store state in external systems (artifact registries, Git, databases), and back up JENKINS_HOME regularly.

Setting up Jenkins with Docker

You can run the Jenkins controller and a Docker-capable build agent using Docker Compose. This is convenient for local development and demonstrations. Persist Jenkins home to keep configuration and job history.

docker-compose.yaml Explained

The following file defines two services: the Jenkins controller itself and an inbound build agent that connects back to it.

# docker-compose.yaml
services:
  jenkins:
    image: jenkins/jenkins:lts
    user: root
    ports:
      - "8080:8080"   # UI
      - "50000:50000" # JNLP agents
    volumes:
      - jenkins_home:/var/jenkins_home
      - /var/run/docker.sock:/var/run/docker.sock # optional if building docker on controller

  dind-agent:
    image: jenkins/inbound-agent:latest
    environment:
      - JENKINS_URL=http://jenkins:8080
      - JENKINS_AGENT_NAME=docker-agent
      - JENKINS_SECRET=<from UI>
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock

volumes:
  jenkins_home:

Key points in this file

  • jenkins/jenkins:lts – Long-Term Support version of Jenkins for stability.
  • ports – Exposes the web UI (8080) and the JNLP port (50000) used by agents.
  • jenkins_home volume – Stores jobs, configuration, and build history so that your setup survives container restarts.
  • /var/run/docker.sock – Mounting the host Docker socket allows builds to run docker build directly.
  • dind-agent – An inbound agent image that connects to the controller using JENKINS_URL, JENKINS_AGENT_NAME, and JENKINS_SECRET (configured in the Jenkins UI).
Security note: Mounting the Docker socket grants high privileges. For production, prefer isolated agents or rootless runners.

Managing Agents and Plugins

Agents

Agents are where your builds actually run. The controller orchestrates the work; agents execute the steps.

  • Static agents: Long-lived VMs or containers with required tools. Stable but potentially wasteful at low utilization. Suitable for small setups or special hardware.
  • Ephemeral agents: Provisioned per build on Kubernetes or in the cloud. Cost-efficient, reproducible toolchains, and less configuration drift.
  • Labels: Tag agents by capability (for example, linux && java17, windows, docker). Pipelines can target these labels.

Plugins

  • Keep plugins updated in step with Jenkins LTS and test updates in a staging Jenkins where possible.
  • Use Configuration as Code (JCasC) to store Jenkins system and plugin configuration in Git.
  • Review plugins periodically and remove unused ones to reduce attack surface and simplify upgrades.
Anti-pattern: Installing new plugins directly on a production Jenkins instance without review or backup can cause outages and security issues.

Writing Your First Jenkins Pipeline

The simplest way to start is to create a Jenkinsfile in your repository and point a Multibranch Pipeline job to it. Jenkins will automatically discover branches and pull requests.

Beginner workflow:
  1. Create or use an existing application repository.
  2. Add a Jenkinsfile at the root of the repository.
  3. Set up a Multibranch Pipeline job in Jenkins that points to the repository URL.
  4. Trigger the first build manually and then configure webhooks so future builds start automatically.

The Jenkinsfile

// Jenkinsfile (declarative)
pipeline {
  agent any
  options { timestamps(); ansiColor('xterm') }
  triggers { pollSCM('@daily') } // replace with webhooks in real setups
  tools { jdk 'jdk17' }

  stages {
    stage('Checkout') {
      steps { checkout scm }
    }

    stage('Build') {
      steps { sh 'mvn -B -U -DskipTests package' }
      post { success { archiveArtifacts artifacts: 'target/*.jar', fingerprint: true } }
    }

    stage('Test') {
      steps {
        sh 'mvn -B test'
        junit 'target/surefire-reports/*.xml'
      }
      post { always { publishHTML(target: [reportDir: 'target/site', reportFiles: 'index.html', reportName: 'Site']) } }
    }

    stage('Security & Quality') {
      steps {
        sh 'mvn -B verify -Pdependency-check'
        // e.g., run spotbugs/jacoco here
      }
      post { always { recordIssues enabledForFailure: true, tools: [java(), spotBugs(pattern: '**/spotbugsXml.xml')] } }
    }

    stage('Package & Publish') {
      when { branch 'main' }
      steps {
        withCredentials([usernamePassword(credentialsId: 'nexus-creds', usernameVariable: 'NEXUS_USER', passwordVariable: 'NEXUS_PASS')]) {
          sh 'mvn -B deploy -DskipTests'
        }
      }
    }
  }
}

What each part does

  • pipeline { ... } – Declarative pipeline syntax, easier to read and validate than scripted pipelines.
  • agent any – Runs on any available agent. In larger setups, you typically specify labels (for example, agent { label 'linux && java17' }).
  • options { timestamps(); ansiColor('xterm') } – Adds timestamps to logs and enables colored output for better readability.
  • triggers { pollSCM('@daily') } – Polls SCM for changes once per day. In production, use webhooks so builds trigger on every push.
  • tools { jdk 'jdk17' } – Tells Jenkins to provision a configured JDK (named jdk17 in Global Tool Configuration).
  • Stage: Checkout – checkout scm pulls the source code for the current branch or pull request.
  • Stage: Build – Runs a Maven build without tests (-DskipTests) to compile and package. On success, it archives the generated JAR files.
  • Stage: Test – Executes tests and publishes JUnit results plus an HTML site (for example, Maven site or documentation).
  • Stage: Security & Quality – Runs dependency checks (OWASP plugin) and collects static analysis results (for example, SpotBugs) via recordIssues.
  • Stage: Package & Publish – Only runs on main; uses credentials to deploy to an artifact repository such as Nexus or Artifactory.
Idea: Treat this Jenkinsfile as your “contract” for CI. As your project matures, you can extend it with additional stages (smoke tests, performance tests, deployment) while keeping the logic versioned with your code.

Setting up CI for a Sample Java Application

This section outlines a minimal CI flow for a Java/Maven application and how it integrates with Jenkins.

  1. Create a new Git repository with a Maven or Gradle project and a Jenkinsfile.
  2. Define Java toolchains in Jenkins (Manage Jenkins → Global Tool Configuration).
  3. Configure credentials for artifact registries (for example, Nexus or Artifactory) and source control.
  4. Enable branch indexing via Multibranch Pipeline and configure GitHub or Bitbucket webhooks.
  5. Publish test results (junit), coverage (jacoco), and sites (publishHTML).

pom.xml (important snippets)

# pom.xml (snippets)
<build>
  <plugins>
    <plugin>
      <groupId>org.jacoco</groupId>
      <artifactId>jacoco-maven-plugin</artifactId>
      <version>0.8.12</version>
      <executions>
        <execution>
          <goals>
            <goal>prepare-agent</goal>
          </goals>
        </execution>
      </executions>
    </plugin>
    <plugin>
      <groupId>org.owasp</groupId>
      <artifactId>dependency-check-maven</artifactId>
      <version>10.0.4</version>
    </plugin>
  </plugins>
</build>

What these plugins do

  • JaCoCo Maven Plugin – Instruments your code to measure test coverage. The prepare-agent goal attaches the JaCoCo agent to the JVM during tests.
  • OWASP Dependency-Check – Scans your dependencies against known vulnerabilities (CVEs). Failing the build when severe vulnerabilities exist is a strong security gate.
Goal: After each commit, you know that tests pass, coverage is acceptable, and you are not shipping dependencies with known critical vulnerabilities.

Using Cloud for Dynamic Agent Provisioning

The Kubernetes plugin can be used to spin up ephemeral agents per build. You define Pod templates with required containers and tools. This keeps agents clean and scalable.

Kubernetes-based Jenkinsfile Example

// Jenkinsfile using Kubernetes ephemeral pod
def label = "maven-${UUID.randomUUID().toString()}"
podTemplate(label: label, cloud: 'kubernetes', yaml: '''
apiVersion: v1
kind: Pod
spec:
  serviceAccountName: jenkins
  containers:
    - name: maven
      image: maven:3.9.9-eclipse-temurin-17
      command: ['cat']
      tty: true
      resources:
        requests: { cpu: '250m', memory: '512Mi' }
        limits:   { cpu: '2',    memory: '2Gi' }
    - name: docker
      image: docker:27-cli
      command: ['cat']
      tty: true
      volumeMounts:
        - name: dockersock
          mountPath: /var/run/docker.sock
  volumes:
    - name: dockersock
      hostPath: { path: /var/run/docker.sock }
''') {
  node(label) {
    stage('Build') { container('maven') { sh 'mvn -B -U -DskipTests package' } }
    stage('Image') { container('docker') { sh 'docker build -t registry/app:${GIT_COMMIT} .' } }
  }
}

How this works

  • podTemplate(...) – Tells Jenkins how to create a temporary Kubernetes Pod that will act as the build agent.
  • label – A unique label for this pod so the node(label) block can schedule work onto it.
  • serviceAccountName: jenkins – Service account used by the pod to talk to the Kubernetes API.
  • Containers:
    • maven – Contains the JDK and Maven for building the Java project.
    • docker – Contains the Docker CLI to build images using the mounted Docker socket.
  • stage('Build') – Executes the Maven build inside the maven container.
  • stage('Image') – Builds a Docker image tagged with the current GIT_COMMIT.
Better isolation: For production, consider building container images without the host Docker socket (for example, Kaniko, BuildKit rootless, or buildah) inside the pod.

Shared Pipeline Libraries

Common steps can be extracted into a reusable Jenkins Shared Library. The library is stored in its own Git repository and registered under Manage Jenkins → Global Pipeline Libraries.

Library Structure

repo-root/
  vars/
    ci.groovy           # global step: ci()
    mavenBuild.groovy   # global step: mavenBuild(args)
  src/org/company/ci/
    Utils.groovy        # helper classes
  resources/
    email-template.html

Example: vars/mavenBuild.groovy

// vars/mavenBuild.groovy
def call(String goals = 'clean verify') {
  stage('Maven Build') {
    sh "mvn -B ${goals}"
    junit 'target/surefire-reports/*.xml'
    step([$class: 'JacocoPublisher'])
  }
}

Using the Library from a Jenkinsfile

// Jenkinsfile using the library
@Library('company-ci-lib@v1') _

pipeline {
  agent { label 'linux && java17' }
  stages {
    stage('Checkout') { steps { checkout scm } }
    stage('Build & Test') { steps { mavenBuild('clean verify') } }
  }
}

What this provides

  • DRY Pipelines: Shared steps like mavenBuild live in one place instead of being duplicated across many Jenkinsfiles.
  • Consistency: Every service can have the same quality gates (tests, coverage, static analysis) by default.
  • Centralized improvements: Updating the shared library automatically improves all consuming pipelines.
Benefits: Reusable pipelines, consistent quality checks, faster onboarding, and centralized updates.

Advanced CI/CD Topics

Artifact Strategy

Publish once, promote the same artifact across environments. Track provenance (SLSA), sign with Cosign, and attach SBOMs.

Environments & IaC

Use Terraform for infrastructure and Helm or Kustomize for applications. Keep environment configuration in Git and change it via pull requests.

GitOps

Use Argo CD or Flux to reconcile cluster state from Git; CD becomes a pull-based, auditable loop.

Progressive Delivery

Use tools such as Argo Rollouts or Flagger for canary deployments and automated analysis with metrics and SLO gates.

Compliance

Introduce policy-as-code (OPA, Conftest), change approvals, artifact retention rules, and audit logs.

Secrets

Rotate secrets frequently. Use Vault, KMS, or External Secrets and prefer short-lived tokens over long-lived credentials.

Caching & Speed

Use remote build caches, test splitting, dependency proxies, and elastic agents to keep feedback fast.

Observability

Expose build and deployment events to monitoring so that you can correlate changes with error rates and latency.

Next step: Once you have basic CI/CD working, invest in observability, security, and quality gates. These turn “we can deploy” into “we can deploy confidently.”

Troubleshooting

# Common Jenkins issues
# 1) Hanging builds     → check agent capacity/labels, node logs, and workspace locks.
# 2) SCM webhooks       → verify webhook secret, reachable URL, and multibranch settings.
# 3) Permission errors  → use folders + role strategy; scope credentials minimally.
# 4) Slow pipelines     → enable parallel stages, cache dependencies, use ephemeral cloud agents.
# 5) Flaky tests        → retry with backoff and increase observability for integration tests.
Remember: Keep everything in code (JCasC, Jenkinsfile, Pod templates, Terraform/Helm). Review changes via pull requests and automate promotions between environments.
