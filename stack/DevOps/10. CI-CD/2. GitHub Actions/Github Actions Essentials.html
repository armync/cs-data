Essential Guide to GitHub Actions

1. CI/CD & Where GitHub Actions Fits

Continuous Integration (CI) is the practice of automatically building and testing the application whenever code is pushed. Continuous Delivery/Deployment (CD) is the practice of automatically getting that tested code ready for—or actually into—production.

GitHub Actions is GitHub’s built-in CI/CD and automation engine. You describe automation in YAML files stored in your repository. GitHub reads those files and runs your commands on virtual machines whenever certain events happen (push, pull request, schedule, etc.).

Core idea

“When X happens in this repo, automatically run these steps on a machine that GitHub provides, using this code.”

Benefits

No separate CI server, close to the code, first-class integration with pull requests, releases, issues, and GitHub Packages.

What you automate

Builds, tests, deployments, code quality checks, security scans, scheduled jobs, and any scriptable DevOps task.

Top-level mental model: GitHub Actions = event → workflow → jobs → steps → actions running on runners using data from contexts, with safe access to secrets.

2. Fundamentals of GitHub Actions (In Depth)

In this chapter you’ll see how a workflow actually runs inside GitHub. We focus on three core building blocks:

  • Execution model – how events trigger workflows, jobs and steps.
  • Runners – the machines that execute your jobs (GitHub-hosted vs self-hosted).
  • Actions, contexts & expressions – reusable steps and the “variables” you can use in YAML.

2.1 Execution Model

The execution model describes the lifecycle of a workflow run: from the moment an event happens in the repo (for example a push) to the moment all jobs finish. Understanding this helps you reason about parallelism, dependencies and where to put specific logic.

  1. An event occurs in your repository (for example, a push or a pull request).
  2. GitHub scans all workflow files in .github/workflows/ and finds those whose on: block matches the event.
  3. For each matching workflow:
    • GitHub creates a workflow run (one execution of that workflow).
    • Each job in the workflow is scheduled onto an available runner.
    • Within a job, steps run sequentially and execute shell commands or actions.
  4. Jobs without dependencies run in parallel; those with needs: wait for others.
  5. The workflow result (success/failure) is based on the jobs’ results.

2.2 Runners

A runner is the actual machine that executes your job. There are two main “types” you will use:

  • GitHub-hosted runners – ephemeral VMs that GitHub creates and destroys per job. Come with common tools preinstalled.
  • Self-hosted runners – machines you manage (on-prem, cloud, container). Good when you need special tools, GPUs or private network access.

Example: basic workflow that shows the difference between GitHub-hosted and self-hosted runners:

# .github/workflows/runners-example.yml
name: Runners Fundamentals

on: [push]

jobs:
  github-hosted:
    runs-on: ubuntu-latest             # Use GitHub-provided Ubuntu VM

    steps:
      - uses: actions/checkout@v4      # 1) Fetch the repo on the runner
      - run: |
          echo "Running on GitHub-hosted runner"
          lsb_release -a               # 2) Show OS info from that runner

  self-hosted:
    runs-on: self-hosted              # Target any self-hosted runner

    steps:
      - run: echo "Running on self-hosted runner with custom setup"

2.3 Actions

An action is a reusable unit of work that you can plug into your workflows. Types of actions you’ll commonly see:

  • Official GitHub actions (e.g. actions/checkout, actions/setup-node).
  • Community actions from the Marketplace.
  • Custom actions that you or your org build (see chapter 9).

Actions are combined with your own shell commands to form full workflows.

Example: workflow that combines multiple actions with your own script:

# .github/workflows/actions-fundamentals.yml
name: Actions Fundamentals

on: [push]

jobs:
  demo:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout repo
        uses: actions/checkout@v4          # Official GitHub Action → gets your code

      - name: Setup Node.js
        uses: actions/setup-node@v4        # Official action → installs Node
        with:
          node-version: 18                 # Input: which version

      - name: Run custom script
        run: node ./scripts/say-hello.js   # Your code, using the tools above

2.4 Contexts & Expressions

Contexts are read-only objects that expose metadata about the current run (for example github, env, runner). You access them in YAML using ${{ }} expressions. These let you:

  • Change behaviour based on event type or branch.
  • Inject dynamic values into environment variables, names, messages, etc.
  • Write conditions for jobs/steps using if:.

Example: using contexts to inspect the event and run conditional logic:

# .github/workflows/contexts-example.yml
name: Contexts & Expressions

on: [push, pull_request]

jobs:
  show-contexts:
    runs-on: ubuntu-latest
    steps:
      - name: Show GitHub context
        run: |
          echo "Event:  ${{ github.event_name }}"  # e.g. push or pull_request
          echo "Ref:    ${{ github.ref }}"         # e.g. refs/heads/main
          echo "Actor:  ${{ github.actor }}"       # user who triggered the run

      - name: Run only for feature branches
        if: github.event_name == 'push' && startsWith(github.ref, 'refs/heads/feature/')
        run: echo "This step runs only for pushes to feature/* branches"

3. Basic Building Blocks & Components (Full CI Example)

This chapter puts together the pieces from the fundamentals into a realistic CI pipeline. You’ll see how a typical Node.js project defines:

  • What events trigger the pipeline.
  • How a CI job is structured (env vars, steps).
  • How a security job depends on a build job.

Example: classic CI workflow with build, tests and a follow-up security scan:

# .github/workflows/ci.yml
name: CI Pipeline                            # Name in Actions UI

on:
  push:                                      # When code is pushed
    branches: [ main, develop ]             # Only for these branches
  pull_request:                             # And on PRs targeting main
    branches: [ main ]

jobs:
  build-and-test:                           # Job 1: build & test
    runs-on: ubuntu-latest                  # Use GitHub Linux runner

    env:
      NODE_ENV: test                        # Example job-level env vars
      API_BASE_URL: https://api.example.com

    steps:
      - name: Checkout code
        uses: actions/checkout@v4           # Fetch repo

      - name: Setup Node.js
        uses: actions/setup-node@v4        # Install Node
        with:
          node-version: 18

      - name: Install dependencies
        run: npm ci                         # Deterministic install

      - name: Run tests
        run: npm test

      - name: Show some context
        run: |
          echo "Event:  ${{ github.event_name }}"
          echo "Branch: ${{ github.ref }}"
          echo "Run ID: ${{ github.run_id }}"

  security-scan:                            # Job 2: security scan
    needs: build-and-test                   # Only if CI passed
    runs-on: ubuntu-latest
    permissions:
      contents: read                        # Only minimal permissions
      security-events: write                # Can upload scan results

    steps:
      - uses: actions/checkout@v4
      - name: Run security scanner
        run: ./scripts/security-scan.sh

4. Workflows & Events – Deep Dive

Every workflow has an on: (triggers) section that defines what kinds of events should start it. There are several “types” of triggers you’ll use:

  • Code-based events – push, pull_request, release, etc.
  • Time-based events – schedule with CRON expressions.
  • Manual events – workflow_dispatch, triggered from the UI or API.

Example: workflow that mixes push, PR, scheduled and manual triggers:

# .github/workflows/triggers-example.yml
name: Workflow & Events Demo

on:
  push:
    branches:
      - main                                # Only for main
      - 'release/*'                         # or any release branch
    paths:
      - 'src/**'                            # Ignore doc-only changes
  pull_request:
    types: [opened, synchronize, reopened]  # Different PR event types
  schedule:
    - cron: '0 3 * * *'                     # Nightly at 03:00 UTC (CRON)
  workflow_dispatch:
    inputs:
      environment:
        description: 'Env to run against'
        required: true
        default: 'staging'                  # UI has dropdown/text-input

5. Job Artifacts & Outputs

When jobs run, they often produce outputs (values) and artifacts (files) that you want to reuse later:

  • Job steps outputs – small pieces of data (version numbers, flags) that other jobs can read.
  • Artifacts – built assets (binaries, bundles, test reports) that are uploaded and then downloaded by other jobs.

This is essential for multi-stage pipelines: build once, reuse the same artifacts for tests or deploys.

Example: build job sets an output version and uploads a web bundle; deploy job downloads and uses it:

# .github/workflows/artifacts-and-outputs.yml
name: Artifacts & Outputs

on: [push]

jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      app_version: ${{ steps.version.outputs.version }}   # Expose version outside job
    steps:
      - uses: actions/checkout@v4

      - name: Compute app version
        id: version                                      # Step ID for outputs
        run: echo "version=1.0.${GITHUB_RUN_NUMBER}" >> $GITHUB_OUTPUT
        # ↑ Write "version=..." to $GITHUB_OUTPUT → creates step output "version"

      - name: Build project
        run: npm ci && npm run build

      - name: Upload web build
        uses: actions/upload-artifact@v4
        with:
          name: web-build                                # Artifact logical name
          path: dist/                                    # Folder to store

  deploy:
    needs: build                                         # Wait for build job
    runs-on: ubuntu-latest
    steps:
      - name: Download artifact
        uses: actions/download-artifact@v4
        with:
          name: web-build                                # Same artifact name

      - name: Deploy specific version
        run: echo "Deploying version ${{ needs.build.outputs.app_version }}"

6. Environment Variables & Secrets

Workflows often need configuration values and secrets. GitHub Actions gives you:

  • Environment variables – non-sensitive values that control behaviour (for example NODE_ENV).
  • Secrets – sensitive values like passwords, API tokens and keys, stored encrypted by GitHub.

The key idea: env vars can be defined at workflow, job or step scope; secrets live in GitHub and are accessed via secrets.NAME.

Example: combining workflow-level, job-level and step-level env vars while safely using secrets:

# .github/workflows/env-and-secrets.yml
name: Env & Secrets Fundamentals

on: [push]

env:                                           # Workflow-wide env vars
  GLOBAL_ENV: production                       # Visible in all jobs

jobs:
  example:
    runs-on: ubuntu-latest
    env:
      JOB_ENV: example-job                     # Visible only inside this job

    steps:
      - name: Print env values
        run: |
          echo "Global env: $GLOBAL_ENV"       # from workflow-level env
          echo "Job env:    $JOB_ENV"          # from job-level env
          echo "Step env:   $STEP_ENV"         # from step-level env
        env:
          STEP_ENV: only-this-step             # Visible only to this step

      - name: Use secrets safely
        run: |
          echo "Logging into registry..."
          echo "${{ secrets.REGISTRY_PASSWORD }}" | \
            docker login registry.example.com \
              -u "${{ secrets.REGISTRY_USER }}" --password-stdin
        # REGISTRY_USER / REGISTRY_PASSWORD defined in repo/org secrets

7. Controlling Workflow & Job Execution

As workflows grow, you need control over when they run, how many can run in parallel, and what happens on failures. GitHub Actions provides:

  • Concurrency – group runs to avoid overlapping work on the same branch.
  • Timeouts – hard limits for job duration.
  • Conditions – if: expressions for jobs and steps.
  • continue-on-error – let the workflow continue even if a step fails.

Example: workflow that enforces one CI run per branch and only deploys from main:

# .github/workflows/control-execution.yml
name: Control Execution

on: [push, pull_request]

concurrency:
  group: ci-${{ github.ref }}        # Only one run per branch at a time
  cancel-in-progress: true           # Cancel older runs when new ones start

jobs:
  tests:
    runs-on: ubuntu-latest
    timeout-minutes: 20              # Hard limit on job run time
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm test

  deploy:
    needs: tests
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    # ↑ Deploy only when it's a push on main (never for PRs)
    steps:
      - run: echo "Deploying main branch build..."

  optional-step-example:
    runs-on: ubuntu-latest
    steps:
      - name: Step that may fail
        run: ./flaky-script.sh
        continue-on-error: true      # Workflow continues even if this step fails

      - name: React to failure
        if: failure()                # Runs if any previous step in this job failed
        run: echo "Handling failure (e.g., send Slack notification)"

8. Jobs & Docker Containers

Sometimes you want your job to run inside a specific Docker image or to have services (like Postgres) available. GitHub Actions supports two main container-related “types”:

  • Job container – the whole job runs inside a given Docker image.
  • Service containers – sidecar containers (databases, queues) that your job can connect to.

8.1 Running the whole job in a container

Use this when you want a fully controlled environment (specific Node, Python, system libs) independent of GitHub’s base image. 

# .github/workflows/container-job.yml
name: Container Job

on: [push]

jobs:
  tests:
    runs-on: ubuntu-latest                 # Underlying VM
    container:
      image: node:18-alpine                # But job's steps run in this container
      options: --cpus 2                    # Example Docker run option

    steps:
      - uses: actions/checkout@v4          # Code available inside container FS
      - run: node -v                       # Node from image
      - run: npm ci
      - run: npm test

8.2 Service containers (e.g. Postgres for integration tests)

Service containers are perfect when your tests need external dependencies such as databases, message brokers or caches. Each service gets a logical name and is reachable over the network from your main job. 

# .github/workflows/service-containers.yml
name: Service Containers

on: [push]

jobs:
  integration-tests:
    runs-on: ubuntu-latest

    services:
      postgres:                            # Logical name for this service
        image: postgres:15                 # Docker image
        env:
          POSTGRES_USER: test
          POSTGRES_PASSWORD: test
          POSTGRES_DB: app_db
        ports:
          - 5432:5432                      # Map container port to job network
        options: >-
          --health-cmd="pg_isready"        # Healthcheck to wait until DB is ready
          --health-interval=10s
          --health-timeout=5s
          --health-retries=5

    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run test:integration      # Tests connect to postgres:5432

9. Building & Using Custom Actions (In Depth)

So far we’ve used existing actions. In this chapter, you learn how to create your own actions, so your organisation can reuse common logic. The main “types” are:

  • Composite actions – YAML only, just a reusable bundle of steps.
  • JavaScript actions – Node.js code packaged as an action.
  • Docker actions – run inside a custom container (for more advanced needs).

9.1 Composite action (YAML-only, easiest to start)

Composite actions are great for DRY-ing up repeated workflows. You keep the logic in one place and reuse it via uses: ./path/to/action. 

# .github/actions/setup-node-deps/action.yml
name: 'Setup Node & Install Deps'             # Display name
description: 'Reusable setup for Node projects'
inputs:
  node-version:                                # Action input
    description: 'Node version to use'
    required: true

runs:
  using: "composite"                           # Composite: a set of steps
  steps:
    - name: Setup Node.js
      uses: actions/setup-node@v4
      with:
        node-version: ${{ inputs.node-version }}  # Use input value

    - name: Install dependencies
      run: npm ci
      shell: bash

9.2 Using the composite action in a workflow

Once defined, your composite action behaves like any other action. You reference it by a relative path in the same repo or by owner/repo@version when it’s published. 

# .github/workflows/use-custom-action.yml
name: Use Custom Action

on: [push]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup via custom action
        uses: ./.github/actions/setup-node-deps   # Path to local action
        with:
          node-version: 18                        # Provide required input

      - run: npm test

9.3 JavaScript action (high-level idea)

JavaScript actions let you write more complex logic using Node.js. They’re ideal when you need:

  • Rich input/output handling.
  • HTTP calls, filesystem access, etc.
  • To distribute the action separately (for example via Marketplace).
# action.yml in my-org/hello-js-action
name: 'Hello JS Action'
description: 'Example JavaScript action'
inputs:
  name:
    description: 'Name to greet'
    required: true
runs:
  using: 'node16'
  main: 'dist/index.js'                 # Compiled JS entrypoint (for example from src/index.ts)

Inside dist/index.js you would use the @actions/core package to read inputs, log output, and mark the action success/failure.

// dist/index.js (simplified example)
const core = require('@actions/core');

async function run() {
  try {
    const name = core.getInput('name');        // Read input defined in action.yml
    core.info(`Hello ${name} from JavaScript action!`);  // Log info
  } catch (error) {
    core.setFailed(error.message);             // Mark action failed
  }
}

run();
Conceptual difference: Composite actions = YAML wrapper around multiple steps. JavaScript / Docker actions = executable code packaged as an action, ideal for complex logic or distribution via Marketplace.

10. Security & Permissions (In Depth)

GitHub Actions is powerful, but that also means it can modify your repo, environments and infrastructure. This chapter covers the key security concepts:

  • GITHUB_TOKEN permissions – what the automatic token can do by default.
  • Protected environments – manual approvals and env-specific secrets.
  • Best practices – how to minimise risk when writing workflows.

10.1 GITHUB_TOKEN permissions

Each workflow run gets a special token called GITHUB_TOKEN. You can control its “type” of access (read/write) using the permissions: block at workflow or job level. 

# .github/workflows/permissions.yml
name: Permissions Fundamentals

on: [push]

permissions:                               # Default token permissions for all jobs
  contents: read                           # e.g. clone repo, read files
  pull-requests: write                     # e.g. comment on PRs
  deployments: write                       # e.g. create deployment records

jobs:
  secure-job:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: echo "Running with least-privilege GITHUB_TOKEN"

10.2 Protected environments (manual approvals + env-specific secrets)

Environments in GitHub (staging, production, etc.) can require approvals before jobs using them run. They also allow you to attach env-specific secrets (for example PROD_DB_PASSWORD). 

# .github/workflows/protected-environment.yml
name: Protected Environment

on:
  push:
    branches: [ main ]                     # Only from main

jobs:
  deploy-prod:
    runs-on: ubuntu-latest
    environment:
      name: production                     # Env configured in repo settings
      url: https://app.example.com
    steps:
      - uses: actions/checkout@v4
      - name: Deploy to production
        run: ./deploy-prod.sh              # Executes only after required reviewers approve
        # Environment-level secrets (e.g. PROD_DB_PASSWORD) available as secrets.*

10.3 Security best-practice checklist

  • Use permissions: to minimize what GITHUB_TOKEN can do.
  • Keep all secrets in GitHub Secrets (repo/org/env) and never in code.
  • Pin all third-party actions to tags or SHAs (avoid @main).
  • Use OIDC for short-lived cloud credentials instead of long-lived keys.
  • Enable built-in security features (code scanning, Dependabot, secret scanning).

11. Debugging Patterns & Interview Phrases

Workflows will break. This chapter focuses on debugging techniques and some phrases that help you explain GitHub Actions clearly in interviews or design reviews.

  • How to inspect contexts to see exactly what event data looks like.
  • How to add extra logging to flaky steps.
  • How to talk about GitHub Actions at a high level.

Example: workflow you can run manually to dump context and log flaky behaviour:

# .github/workflows/debugging.yml
name: Debugging Patterns

on: [workflow_dispatch]                        # Run manually from the UI

jobs:
  debug:
    runs-on: ubuntu-latest
    steps:
      - name: Print full GitHub context
        run: echo '${{ toJson(github) }}'      # See event payload, refs, etc.

      - name: Extra logging around flaky script
        run: |
          echo "Starting script at $(date)"
          ./flaky-script.sh || echo "Script exited with code $?"
          echo "Finished at $(date)"
Interview soundbites:
  • “GitHub Actions executes workflows on runners in response to events. Workflows are composed of jobs, which contain steps that run actions or shell commands.”
  • “We use contexts & expressions to make workflows dynamic (branch-based behavior, conditional deploys, path filters).”
  • “We treat CI/CD as code: workflows and custom actions live in the repo, are reviewed, versioned, and shared across projects.”
