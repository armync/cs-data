Cloud Essentials

Introduction

Cloud computing delivers compute, storage, networking, databases, and higher-level services over the internet. It trades capital expenditure for operational expenditure and enables elastic scaling, global reach, and programmable infrastructure.

Service Models

  • IaaS: Virtual machines, storage, networks you manage.
  • PaaS: Managed runtimes/databases where you bring code & data.
  • SaaS: Complete applications delivered as a service.

Deployment Models

  • Public Cloud: Shared provider infrastructure.
  • Private: Dedicated environment (hosted or on‑prem).
  • Hybrid: Mix of on‑prem and public cloud.
  • Multi‑Cloud: Using multiple public clouds.

Cloud Building Blocks (Basics)

Accounts & Tenants

  • AWS Account / Azure Subscription under a tenant (Entra ID).
  • Use separate accounts/subscriptions for prod, stage, dev.

Regions & AZs

  • Region: Geographical location (e.g., eu-west-1, West Europe).
  • Availability Zone (AZ): Independent data centers inside a region.
  • Design for multi‑AZ for high availability.

Edge Locations

  • CDN and edge services operate closer to users for latency and caching.

Services 101

  • Compute: EC2 / Azure VMs.
  • Object Storage: S3 / Blob Storage.
  • Databases: RDS/Aurora / Azure SQL, PostgreSQL, MySQL.
  • Networking: VPC / VNet, subnets, routing, gateways.
  • Identity: IAM / Entra ID & RBAC; Key management: KMS / Key Vault.
Rule of thumb: Pick a single region near your users/data, then spread across multiple AZs.

Learn the Cloud Operating Model

  • APIs over Hardware: Everything is programmable; use Infrastructure as Code (IaC).
  • On‑Demand: Provision resources when needed; automate teardown.
  • Managed Services: Offload undifferentiated heavy lifting (patching, HA).
  • Scaling by Default: Auto‑scale groups, serverless, and managed databases.
# Example: create a resource group & VM on Azure (CLI)
az group create -n rg-demo -l westeurope
az vm create -g rg-demo -n vm1 --image Ubuntu2204 --size Standard_B2s --public-ip-sku Standard

# Example: create an EC2 instance on AWS (CLI)
aws ec2 run-instances --image-id ami-xyz --instance-type t3.micro --subnet-id subnet-abc --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=vm1}]'

Grasp the Shared Responsibility Model

Provider Secures

  • Physical data centers, power, cooling
  • Global backbone network
  • Hypervisor and underlying hardware
  • Managed service control planes

You Secure

  • Identity & access (users, roles, keys)
  • Data (classification, encryption, backups)
  • Network boundaries (subnets, security groups/NSGs)
  • Configuration & patching of what you manage
Tip: Document who owns what for every service you deploy.

Think Security First

  • Start with least privilege policies; grant narrowly and review regularly.
  • Rotate credentials and prefer short‑lived tokens over static keys.
  • Encrypt in transit (TLS) and at rest (KMS/Key Vault managed keys).
  • Segment networks; deny‑by‑default security groups/NSGs.

Networking Fundamentals

VPC / VNet Topology

  • VPC (AWS) / VNet (Azure): Your isolated virtual network with a CIDR (e.g., 10.0.0.0/16).
  • Subnets: Split the CIDR into public and private subnets, ideally per AZ.
  • Route Tables: Control where traffic goes (e.g., to Internet Gateway, NAT Gateway, peering).
  • Security Groups / NSGs: Stateful firewalls at instance/NIC level.
  • NACLs (AWS): Optional stateless subnet firewalls.

Public vs Private Subnets

Subnet TypeInboundOutboundTypical Workloads
PublicAllowed from internet via Internet Gateway (IGW) + public IP.Direct to internet via IGW.Load balancers, bastion, NAT gateways.
PrivateNo direct internet inbound.Outbound internet via NAT Gateway (AWS) / NAT Gateway (Azure) in a public subnet.App servers, databases, internal services.

Gateways & Linking Components

  • Internet Gateway (AWS) / Public IP + default route (Azure): Enables internet access for public subnets.
  • NAT Gateway: Deployed in a public subnet; private subnets route 0.0.0.0/0 to it for outbound internet.
  • PrivateLink / Private Endpoint: Private access to SaaS/cloud services without traversing the public internet.
  • Peering / VNet Peering: Connect two VPCs/VNets privately; update route tables accordingly.
  • Transit Gateway / Virtual WAN: Hub‑and‑spoke connectivity at scale.
# Minimal public/private design (AWS CLI concepts)
# 1) Create VPC & subnets per AZ
aws ec2 create-vpc --cidr-block 10.0.0.0/16
# ... create subnets: 10.0.0.0/24 (public-a), 10.0.1.0/24 (private-a), etc.
# 2) Attach Internet Gateway and route 0.0.0.0/0 from public route table to IGW
# 3) Create NAT Gateway in public-a; route private subnets' 0.0.0.0/0 to NAT GW
# 4) Place ALB in public; app servers in private; DB in isolated private

# Minimal public/private design (Azure CLI concepts)
az network vnet create -g rg -n vnet --address-prefix 10.1.0.0/16 \
  --subnet-name public --subnet-prefix 10.1.0.0/24
az network vnet subnet create -g rg --vnet-name vnet -n private --address-prefix 10.1.1.0/24

Cloud Backbone Networks

Hyperscalers operate private global backbones (e.g., AWS Global Network, Azure Backbone) interconnecting regions and edge locations for lower latency and improved reliability compared to the public internet.

Identities & Access

Service Principal / Non‑Human Identity

Use programmatic identities for automation and workloads (CI/CD, apps). Prefer managed identities tied to compute where available.

# Azure: create a service principal
az ad sp create-for-rbac --name app-sp --role Contributor --scopes /subscriptions/<subId>/resourceGroups/rg-demo
# Output includes appId (client id) and password (client secret)

# AWS: create a role for an application with least-privilege policy
aws iam create-role --role-name app-role --assume-role-policy-document file://trust.json
aws iam put-role-policy --role-name app-role --policy-name app-inline --policy-document file://least-priv.json

Least Privilege

  • Start from Deny All and add only what the workload needs.
  • Scope by resource and action; separate duties for deploy vs operate.
  • Use access reviews and time‑bound elevation (PIM/temporary credentials).

Connectivity & SSH

SSH

Use SSH to securely administer Linux VMs. Prefer key‑based auth or one‑time short‑lived certs. Disable password logins and root SSH where possible.

# Generate an Ed25519 key and connect
ssh-keygen -t ed25519 -C "you@example.com"
ssh -i ~/.ssh/id_ed25519 ubuntu@<public-ip-or-dns>

# SSH through a bastion host (ProxyJump)
ssh -J bastion@bastion.example.com app@10.1.1.10

Bastion / Jump Host

  • Hardened entry point in a public subnet to reach private resources.
  • Restrict inbound to your office/VPN IP ranges; log all sessions.
  • Alternatives: AWS Systems Manager Session Manager, Azure Bastion (agentless).

SSL/TLS, Certificate Authorities, and Automation

TLS encrypts data in transit. Certificates are issued by Certificate Authorities (CAs). Use managed certs or automate issuance/renewal (e.g., ACME/Let’s Encrypt).

# Check a server's TLS cert chain
openssl s_client -connect example.com:443 -servername example.com -showcerts < /dev/null

# Request/renew via certbot (Let’s Encrypt)
sudo certbot certonly --dns-route53 -d api.example.com

Observability & Logging (Logging Isn’t Free)

  • Collect metrics, logs, and traces for visibility.
  • Define retention by environment (e.g., 7–14 days for dev, 30–90 for prod).
  • Sample traces, filter high‑volume logs, and archive to cold storage to control cost.
# AWS: set log retention (example via CLI)
aws logs put-retention-policy --log-group-name /prod/api --retention-in-days 30

# Azure: set diagnostic settings to archive to storage
az monitor diagnostic-settings create -g rg-demo -n diagToStorage \
  --resource <resourceId> --storage-account <saName> --logs '[{"category":"AppServiceHTTPLogs","enabled":true}]'

Know the Cost of Ownership

  • Egress Costs: Data leaving the provider network incurs charges.
  • Idle resources still cost money (disks, IPs, NAT gateways, snapshots).
  • Right‑size instances; use spot/preemptible where appropriate.
  • Adopt budgets and alerts; tag for showback/chargeback.
# AWS: simple budget alert (example snippet)
aws budgets create-budget --account-id <acct> --budget file://budget.json

# Azure: cost management export (example snippet)
az costmanagement export create --name monthly --type ActualCost --scope /subscriptions/<subId>

Storage & Data Management

Lifecycle Rules

Move infrequently accessed data to colder tiers automatically to save cost.

# AWS S3 lifecycle (JSON excerpt)
{
  "Rules": [{
    "ID": "logs-archive",
    "Filter": {"Prefix": "logs/"},
    "Status": "Enabled",
    "Transitions": [{"Days": 30, "StorageClass": "STANDARD_IA"}],
    "NoncurrentVersionTransitions": [{"NoncurrentDays": 30, "StorageClass": "GLACIER"}]
  }]
}

# Azure Blob lifecycle (rule snippet)
{
  "name": "logs-archive",
  "type": "Lifecycle",
  "definition": {
    "actions": {"baseBlob": {"tierToCool": {"daysAfterModificationGreaterThan": 30}}},
    "filters": {"blobTypes": ["blockBlob"], "prefixMatch": ["logs/"]}
  }
}

Resource Tagging (Follow the Money)

  • Standardize keys: env, owner, cost-center, application, data-classification.
  • Enforce via policy (AWS Tag Policies / Azure Policy) and CI checks.
# AWS: tag a resource
aws ec2 create-tags --resources i-abc123 --tags Key=env,Value=prod Key=owner,Value=team-x

# Azure: tag a resource group
az group update -n rg-demo --set tags.env=prod tags.owner=team-x

High Availability (HA) — Applications and Clusters

  • Design for AZ failure: deploy across multiple Availability Zones.
  • Use managed HA: load balancers, multi‑AZ databases, auto‑scaling.
  • Chaos testing & runbooks; regular backup+restore drills.
# AWS: ALB + target group (conceptual CLI)
aws elbv2 create-load-balancer --name web-alb --subnets subnet-a subnet-b
aws elbv2 create-target-group --name web-tg --vpc-id vpc-xyz --protocol HTTP --port 80

# Azure: Standard Load Balancer / Application Gateway (conceptual CLI)
az network lb create -g rg-demo -n web-lb --sku Standard --frontend-ip-name fe1 --backend-pool-name be1

CVE & GHSA (Vulnerability Identifiers)

  • CVE: Common identifiers for publicly known vulnerabilities.
  • GHSA: GitHub Security Advisories, often linked to CVEs, focused on developer ecosystems.
  • Track advisories for OS images, containers, libraries, and managed services; patch promptly.

Quick Reference Checklists

Before You Deploy

  • Define owner, RTO/RPO, and data classification.
  • Plan VPC/VNet CIDRs, subnets, routing, and peering.
  • Decide tagging keys: env, owner, cost-center.
  • Pick logging strategy and retention.

Security Essentials

  • Least‑privilege IAM roles; short‑lived credentials.
  • TLS everywhere; managed certificates where possible.
  • Private subnets + NAT; bastion/SSM for admin access.
  • Automated patching and CVE/GHSA monitoring.

Cost Hygiene

  • Budgets and alerts per account/subscription.
  • Lifecycle rules for logs and data.
  • Turn off idle resources; watch egress and NAT gateways.
  • Rightsize and reserve/commit where stable.
