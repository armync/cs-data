Kubernetes Essentials Guide

From fundamentals to production deployment with cloud infrastructure

Introduction to Kubernetes

Kubernetes, often abbreviated as K8s (the "8" represents the eight letters between "K" and "s"), is an open-source container orchestration platform originally developed by Google and now maintained by the Cloud Native Computing Foundation. It provides a framework for running distributed systems resiliently, handling scaling, failover, and deployment patterns for your applications.

What Problems Does Kubernetes Solve?

Before Kubernetes, deploying containerized applications at scale presented several challenges. You might run a few containers on a single machine with Docker, but what happens when you need to run hundreds or thousands of containers across multiple machines? How do you ensure they're running, restart them when they fail, and route traffic to the right place? How do you handle deployments without downtime?

Kubernetes addresses these challenges by providing:

Orchestration

Automatically schedules containers across multiple machines, deciding where each container should run based on available resources and constraints.

Self-Healing

Monitors container health and automatically restarts failed containers, replaces containers, and kills containers that don't respond to health checks.

Scaling

Scales applications up and down automatically based on CPU usage or other metrics, or manually with simple commands.

Service Discovery

Provides built-in service discovery and load balancing, giving containers stable DNS names and distributing traffic across healthy instances.

Automated Rollouts

Gradually rolls out changes to your application or its configuration while monitoring health, rolling back if something goes wrong.

Secret Management

Stores and manages sensitive information like passwords, OAuth tokens, and SSH keys securely.

Where Kubernetes Fits in the Container Ecosystem

LayerExamplesResponsibility
Container Image Docker, Podman, BuildKit Packages application code and dependencies into a standardized unit.
Container Runtime containerd, CRI-O, Docker Engine Actually runs containers on a host operating system.
Orchestrator Kubernetes, Nomad, Docker Swarm Manages containers across multiple machines, handles scheduling, networking, and scaling.

Key Understanding: Kubernetes doesn't replace Docker or other container runtimes. Instead, it works with them. Think of Docker as the engine that runs a single container, while Kubernetes is the orchestrator that manages thousands of containers across many machines.

When Should You Use Kubernetes?

Kubernetes is powerful, but it comes with complexity. Consider using Kubernetes when:

  • You're running multiple containerized applications that need to communicate
  • You need to scale applications dynamically based on demand
  • You require high availability and can't afford significant downtime
  • You're deploying across multiple environments (dev, staging, production)
  • Your team is already comfortable with containers and infrastructure as code

You might not need Kubernetes if:

  • You're running a simple application on a single server
  • Your application doesn't require scaling or high availability
  • Your team is small and lacks DevOps expertise
  • Simpler solutions like managed PaaS platforms meet your needs

Local Development Options

You don't need a full cloud cluster to learn Kubernetes. Several tools let you run Kubernetes on your local machine:

  • Rancher Desktop - Provides a graphical interface with Kubernetes and container runtime, making it easy to get started on Windows, Mac, or Linux.
  • minikube - The original single-node local Kubernetes cluster, great for learning and testing. Supports various drivers including Docker, VirtualBox, and Hyperkit.
  • kind (Kubernetes in Docker) - Runs Kubernetes clusters inside Docker containers. Faster than VM-based solutions and popular for CI/CD testing.
  • Docker Desktop - Includes a single-node Kubernetes cluster built-in on Mac and Windows.
  • k3s/k3d - Lightweight Kubernetes distribution that uses fewer resources, perfect for edge computing or local development.
Recommendation: Start with minikube or Rancher Desktop for learning. They provide good documentation and closely mirror production Kubernetes behavior. Once comfortable, explore kind for its speed or k3s for resource-constrained environments.

Kubernetes Architecture

Understanding Kubernetes architecture is crucial for effective troubleshooting and deployment. A Kubernetes cluster consists of at least one control plane and one or more worker nodes. Let's break down each component.

Control Plane Components

The control plane makes global decisions about the cluster and detects and responds to cluster events. In production, the control plane typically runs on multiple nodes for high availability.

kube-apiserver

The API server is the front door to Kubernetes. Every interaction with the cluster goes through it, whether you're using kubectl, a CI/CD system, or an application inside the cluster. It validates and processes REST requests, updating the corresponding objects in etcd. The API server is the only component that talks directly to etcd.

etcd

etcd is a consistent and highly-available key-value store used as Kubernetes' backing store for all cluster data. Everything you create in Kubernetes (pods, services, secrets) ultimately gets stored in etcd. If you lose etcd data, you lose your cluster state. This is why backing up etcd is critical in production environments.

kube-scheduler

The scheduler watches for newly created pods that don't have a node assigned yet, and selects a node for them to run on. It considers factors like resource requirements, hardware/software/policy constraints, affinity and anti-affinity specifications, data locality, and inter-workload interference. The scheduler doesn't actually start the pod; it just assigns it to a node.

kube-controller-manager

This component runs controller processes that regulate the state of the cluster. Each controller is a separate process, but they're all compiled into a single binary and run in a single process. Controllers include:

  • Node controller - Monitors node health and responds when nodes go down
  • Replication controller - Maintains the correct number of pods for each replica set
  • Endpoints controller - Populates the Endpoints object (joins Services and Pods)
  • Service Account & Token controllers - Create default accounts and API access tokens for new namespaces

cloud-controller-manager

This component embeds cloud-specific control logic, letting you link your cluster into your cloud provider's API. It only runs controllers that are specific to your cloud provider. For example, on AWS it manages load balancers when you create a Service of type LoadBalancer.

Node Components

Node components run on every node, maintaining running pods and providing the Kubernetes runtime environment.

kubelet

The kubelet is the primary node agent. It watches the API server for pods that have been assigned to its node and ensures those containers are running and healthy. The kubelet doesn't manage containers that weren't created by Kubernetes. It takes a set of PodSpecs and ensures the containers described in those PodSpecs are running.

kube-proxy

kube-proxy maintains network rules on nodes, allowing network communication to your pods from inside or outside the cluster. It uses the operating system packet filtering layer if available, otherwise it forwards traffic itself. This is what makes Services work and handles load balancing across pod replicas.

Container Runtime

The container runtime is the software responsible for running containers. Kubernetes supports several container runtimes including containerd, CRI-O, and any implementation of the Kubernetes Container Runtime Interface (CRI). Docker Engine no longer works directly as of Kubernetes 1.24, but containerd (which Docker uses underneath) works fine.

Add-ons

Add-ons use Kubernetes resources to implement cluster features. They're not technically part of the core Kubernetes system, but most clusters need some of them:

  • DNS - Cluster DNS is a DNS server that serves DNS records for Kubernetes services. Containers started by Kubernetes automatically include this DNS server in their DNS searches.
  • Web UI (Dashboard) - A general-purpose web UI for Kubernetes clusters that lets you manage applications and troubleshoot them.
  • Container Resource Monitoring - Records metrics about containers in a central database and provides a UI for browsing that data.
  • Cluster-level Logging - Saves container logs to a central log store with search and browsing interface.

Communication Flow

Here's what happens when you create a deployment:

  1. You run kubectl apply which sends your deployment YAML to the API server
  2. The API server validates the request and stores it in etcd
  3. The deployment controller (part of controller-manager) notices the new deployment and creates a ReplicaSet
  4. The ReplicaSet controller notices it needs to create pods and creates pod objects
  5. The scheduler notices unscheduled pods and assigns them to nodes with enough resources
  6. The kubelet on each assigned node notices it has new pods to run
  7. The kubelet tells the container runtime to pull images and start containers
  8. Once running, the kubelet continuously monitors pod health and reports back to the API server
Important Pattern: Kubernetes follows a declarative model with control loops. You declare desired state (I want 3 replicas), and controllers continuously work to make actual state match desired state. This is fundamentally different from imperative systems where you issue direct commands.

Core Kubernetes Concepts

Before diving into commands and configurations, you need to understand the fundamental building blocks of Kubernetes. These concepts appear everywhere in Kubernetes, so solid understanding here will make everything else easier.

Understanding Labels and Selectors

Labels are one of the most important concepts in Kubernetes because they're how objects find and refer to each other. A label is simply a key-value pair like app: nginx or environment: production. You can attach multiple labels to any object.

Selectors use labels to identify groups of objects. When a Service needs to find its pods, or when a Deployment creates pods, they use selectors. This loose coupling is powerful because you can change which pods belong to a service just by changing labels, without modifying the service definition.

Key Principle: In production, you rarely create Pods directly. Instead, you create higher-level controllers like Deployments or StatefulSets that create and manage Pods for you. This ensures Pods are recreated if they fail and allows for controlled updates.

kubectl Essentials

kubectl is your primary tool for interacting with Kubernetes clusters. It communicates with the cluster's API server using configuration stored in a kubeconfig file (usually at ~/.kube/config). This file contains cluster information, authentication credentials, and context definitions.

kubectl get namespaces                  # List all namespaces

Pods and Deployments

Understanding Pods

A Pod is the smallest unit you can deploy in Kubernetes. It represents a single instance of a running process in your cluster. Most pods contain just one container, but you can have multiple containers in a pod when they need to share resources tightly (like a main application container and a logging sidecar).

All containers in a pod:

  • Share the same network namespace (same IP address and port space)
  • Can communicate via localhost
  • Share the same storage volumes
  • Are scheduled together on the same node
  • Are created and destroyed together

A Basic Pod Definition

While you won't create pods directly in production, understanding their structure is essential.

apiVersion: v1
kind: Pod
metadata:
  name: simple-web
  labels:
    app: web
    tier: frontend
spec:
  containers:
    - name: nginx
      image: nginx:1.27-alpine
      ports:
        - containerPort: 80
          name: http
      resources:
        requests:
          cpu: "100m"
          memory: "128Mi"
        limits:
          cpu: "500m"
          memory: "512Mi"
Breaking down this Pod YAML:
  • apiVersion – Which version of the Kubernetes API this resource uses.
  • kind – The type of object. Here it is a Pod.
  • metadata.name – The name of the Pod; must be unique within the namespace.
  • metadata.labels – Key–value tags used to group and select objects (for example, by a Service or Deployment).
  • spec – Describes the desired state of the object — what you want Kubernetes to run.
  • spec.containers – The list of containers that should run inside this Pod.
  • containers[].name – A human‑readable name for the container inside the Pod.
  • containers[].image – The container image to run (from a registry like Docker Hub or ECR).
  • containers[].ports[].containerPort – The port the application inside the container listens on.
  • resources.requests – The minimum CPU/memory the Pod needs so the scheduler can place it on a node.
  • resources.limits – The maximum CPU/memory the container is allowed to use.

This creates a single pod running Nginx. However, if the node fails or the pod crashes, it won't be recreated automatically. That's why we use Deployments in practice.

Deployments: Managing Pod Lifecycles

A Deployment provides declarative updates for Pods and ReplicaSets. You describe a desired state, and the Deployment controller changes the actual state to match at a controlled rate. Deployments handle rolling updates, rollbacks, and ensure the specified number of pod replicas are running. 

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-deployment
  labels:
    app: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: nginx
          image: nginx:1.27-alpine
          ports:
            - containerPort: 80
          resources:
            requests:
              cpu: "100m"
              memory: "128Mi"
            limits:
              cpu: "500m"
              memory: "512Mi"
          # Probes omitted here for brevity; see the
          # "Health Checks" section for full examples.

What Happens When You Apply This?

  1. Kubernetes creates a Deployment object named "web-deployment"
  2. The Deployment controller creates a ReplicaSet with the desired template
  3. The ReplicaSet controller creates 3 Pods with the label app=web
  4. The scheduler assigns each Pod to a node with sufficient resources
  5. The kubelet on each node pulls the image and starts containers
  6. If any Pod fails, the ReplicaSet creates a replacement
  7. If a node fails, Pods are rescheduled on healthy nodes

Health Checks: Liveness and Readiness Probes

Probes let Kubernetes know if your application is healthy and ready to serve traffic. This is crucial for zero-downtime deployments and automatic recovery.

Liveness Probe

Tells Kubernetes if the container is alive. If the probe fails, Kubernetes kills the container and restarts it. Use this to catch deadlocks or infinite loops where the process is running but not functioning.

Readiness Probe

Tells Kubernetes if the container is ready to accept traffic. If it fails, the Pod is removed from Service endpoints, so it won't receive traffic. Use this during startup or when temporarily unable to handle requests (like during cache warming). 

# HTTP probe
livenessProbe:
  httpGet:
    path: /healthz
    port: 8080
  initialDelaySeconds: 15
  periodSeconds: 10

# TCP probe
livenessProbe:
  tcpSocket:
    port: 8080
  initialDelaySeconds: 15
  periodSeconds: 10

# Command probe
livenessProbe:
  exec:
    command:
      - cat
      - /tmp/healthy
  initialDelaySeconds: 5
  periodSeconds: 5

Rolling Updates and Rollbacks

Deployments excel at handling updates with zero downtime. When you update the image or configuration:

# Update image
kubectl set image deployment/web-deployment nginx=nginx:1.27.1-alpine

# Or edit the YAML file and apply
kubectl apply -f deployment.yaml

# Watch the rollout
kubectl rollout status deployment/web-deployment

# View rollout history
kubectl rollout history deployment/web-deployment

# Rollback to previous version
kubectl rollout undo deployment/web-deployment

# Rollback to specific revision
kubectl rollout undo deployment/web-deployment --to-revision=2

# Pause a rollout (useful if issues detected)
kubectl rollout pause deployment/web-deployment

# Resume after fixing issues
kubectl rollout resume deployment/web-deployment

Controlling Rollout Strategy

spec:
  replicas: 10
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 2          # Max pods above desired count during update
      maxUnavailable: 1    # Max pods unavailable during update

With these settings, Kubernetes will create up to 2 new pods before killing old ones, and never have more than 1 pod unavailable. This ensures smooth transitions with minimal risk.

StatefulSets: For Stateful Applications

While Deployments work great for stateless applications, StatefulSets are designed for stateful applications like databases that need stable network identities and persistent storage. 

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
spec:
  serviceName: postgres
  replicas: 3
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
        - name: postgres
          image: postgres:16
          ports:
            - containerPort: 5432
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 10Gi

StatefulSets provide:

  • Stable network identifiers (postgres-0, postgres-1, postgres-2)
  • Stable persistent storage
  • Ordered deployment and scaling
  • Ordered automated rolling updates

Services and Ingress: Networking in Kubernetes

The Problem Services Solve

Pods are ephemeral. They get created and destroyed constantly, getting new IP addresses each time. You can't rely on Pod IPs for communication. Services provide a stable endpoint that automatically routes traffic to healthy Pods matching a label selector.

ClusterIP: Internal Service

The default Service type exposes the service on an internal IP in the cluster. This type makes the service only reachable from within the cluster. 

apiVersion: v1
kind: Service
metadata:
  name: web-service
spec:
  selector:
    app: web
  ports:
    - protocol: TCP
      port: 80
      targetPort: 80
  type: ClusterIP

Now any pod in the cluster can reach your web pods at web-service:80 or web-service.default.svc.cluster.local:80. Kubernetes DNS handles the name resolution.

NodePort: External Access via Node IP

NodePort exposes the Service on each Node's IP at a static port. You can then access the Service from outside the cluster by requesting NodeIP:NodePort. 

apiVersion: v1
kind: Service
metadata:
  name: web-nodeport
spec:
  type: NodePort
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 80
      nodePort: 30080    # Optional, Kubernetes assigns one if not specified

This Service is now accessible at any-node-ip:30080. NodePort services are useful for development or when you don't have a cloud load balancer, but they're not ideal for production.

LoadBalancer: Cloud Load Balancer

In cloud environments, LoadBalancer type creates an external load balancer in your cloud provider's infrastructure. This is the most common way to expose services to the internet in production. 

apiVersion: v1
kind: Service
metadata:
  name: web-loadbalancer
spec:
  type: LoadBalancer
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 80

The cloud provider provisions a load balancer and assigns it an external IP. You can find this IP with kubectl get service web-loadbalancer.

Headless Services

Sometimes you don't want load balancing or a single Service IP. Headless services let clients connect directly to Pod IPs. This is useful for StatefulSets or when doing client-side load balancing. 

apiVersion: v1
kind: Service
metadata:
  name: postgres-headless
spec:
  clusterIP: None    # This makes it headless
  selector:
    app: postgres
  ports:
    - port: 5432

Ingress: HTTP(S) Routing

Ingress exposes HTTP and HTTPS routes from outside the cluster to services within the cluster. It can provide load balancing, SSL termination, and name-based virtual hosting. Think of it as a sophisticated reverse proxy.

Before you can use Ingress, you need an Ingress Controller running in your cluster. Popular choices include NGINX Ingress Controller, Traefik, HAProxy, and cloud-specific controllers like AWS ALB Ingress Controller.

Basic Ingress Example

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  rules:
    - host: myapp.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-service
                port:
                  number: 80

Multiple Services with Path-based Routing

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: multi-service-ingress
spec:
  ingressClassName: nginx
  rules:
    - host: myapp.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api-service
                port:
                  number: 8080
          - path: /web
            pathType: Prefix
            backend:
              service:
                name: web-service
                port:
                  number: 80

TLS/SSL Configuration

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: tls-ingress
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - myapp.example.com
      secretName: tls-secret    # Must contain tls.crt and tls.key
  rules:
    - host: myapp.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-service
                port:
                  number: 80
cert-manager Integration: In production, use cert-manager to automatically provision and renew Let's Encrypt certificates. It integrates seamlessly with Ingress resources and handles all the complexity of certificate management.

Network Policies

By default, all pods can communicate with all other pods. Network Policies let you control traffic between pods for security. They work like firewall rules. 

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-network-policy
spec:
  podSelector:
    matchLabels:
      app: api
  policyTypes:
    - Ingress
    - Egress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: web
      ports:
        - protocol: TCP
          port: 8080
  egress:
    - to:
        - podSelector:
            matchLabels:
              app: database
      ports:
        - protocol: TCP
          port: 5432

This policy allows the api pods to receive traffic only from web pods on port 8080, and allows api pods to send traffic only to database pods on port 5432.

Configuration and Storage

ConfigMaps: Application Configuration

ConfigMaps store non-confidential configuration data in key-value pairs. They decouple configuration from container images, making applications more portable.

Creating ConfigMaps

# From literal values
kubectl create configmap app-config \
  --from-literal=LOG_LEVEL=info \
  --from-literal=API_URL=https://api.example.com

# From a file
kubectl create configmap nginx-config --from-file=nginx.conf

# From a directory
kubectl create configmap app-configs --from-file=./configs/

# From YAML
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  LOG_LEVEL: "info"
  API_URL: "https://api.example.com"
  config.json: |
    {
      "database": {
        "host": "db.example.com",
        "port": 5432
      }
    }

Using ConfigMaps in Pods

spec:
  containers:
    - name: app
      image: myapp:1.0
      # As environment variables
      envFrom:
        - configMapRef:
            name: app-config
      # Or individual env vars
      env:
        - name: LOG_LEVEL
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: LOG_LEVEL
      # As volume mount
      volumeMounts:
        - name: config
          mountPath: /etc/config
  volumes:
    - name: config
      configMap:
        name: app-config

Secrets: Sensitive Data

Secrets are similar to ConfigMaps but intended for sensitive information. They're base64-encoded (not encrypted by default) and have additional access controls. For true encryption at rest, integrate with cloud KMS or use solutions like Sealed Secrets or External Secrets Operator.

Creating Secrets

# From literal values
kubectl create secret generic db-credentials \
  --from-literal=username=admin \
  --from-literal=password=secretpassword

# From files
kubectl create secret generic tls-secret \
  --from-file=tls.crt=./cert.pem \
  --from-file=tls.key=./key.pem

# From YAML (values must be base64-encoded)
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
type: Opaque
data:
  username: YWRtaW4=        # base64 of "admin"
  password: c2VjcmV0cGFzc3dvcmQ=  # base64 of "secretpassword"

Using Secrets in Pods

spec:
  containers:
    - name: app
      image: myapp:1.0
      env:
        - name: DB_USERNAME
          valueFrom:
            secretKeyRef:
              name: db-credentials
              key: username
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: db-credentials
              key: password
      # Or mount as files
      volumeMounts:
        - name: secrets
          mountPath: /etc/secrets
          readOnly: true
  volumes:
    - name: secrets
      secret:
        secretName: db-credentials

Persistent Storage

Containers are ephemeral, but applications often need persistent data. Kubernetes provides an abstraction layer for storage that works across different infrastructure providers.

Storage Classes

StorageClasses define different types of storage available in your cluster. Cloud providers typically create default storage classes automatically. 

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
provisioner: kubernetes.io/aws-ebs
parameters:
  type: gp3
  iops: "3000"
  throughput: "125"
reclaimPolicy: Delete
allowVolumeExpansion: true

PersistentVolumeClaims

A PersistentVolumeClaim (PVC) is a request for storage. When you create a PVC, Kubernetes finds or provisions a PersistentVolume that satisfies the request. 

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: database-storage
spec:
  accessModes:
    - ReadWriteOnce    # Single node read-write
  storageClassName: fast-ssd
  resources:
    requests:
      storage: 50Gi

Access modes:

  • ReadWriteOnce (RWO) - Volume can be mounted read-write by a single node
  • ReadOnlyMany (ROX) - Volume can be mounted read-only by many nodes
  • ReadWriteMany (RWX) - Volume can be mounted read-write by many nodes

Using PVCs in Pods

apiVersion: v1
kind: Pod
metadata:
  name: database
spec:
  containers:
    - name: postgres
      image: postgres:16
      volumeMounts:
        - name: data
          mountPath: /var/lib/postgresql/data
      env:
        - name: POSTGRES_PASSWORD
          valueFrom:
            secretKeyRef:
              name: db-credentials
              key: password
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: database-storage

Volume Types

Beyond PersistentVolumes, Kubernetes supports many volume types for different use cases:

  • emptyDir - Temporary storage that exists as long as the Pod exists, shared between containers in a Pod
  • hostPath - Mounts a file or directory from the host node (use sparingly, breaks pod portability)
  • configMap/secret - Mount configuration or secrets as files
  • nfs - Mount an NFS share
  • Cloud provider volumes - awsElasticBlockStore, gcePersistentDisk, azureDisk, etc.
# emptyDir example - shared cache between containers
volumes:
  - name: cache
    emptyDir:
      sizeLimit: 1Gi

# hostPath example - accessing Docker socket
volumes:
  - name: docker-sock
    hostPath:
      path: /var/run/docker.sock
      type: Socket

Advanced Topics

Resource Requests and Limits

Resource management is critical for cluster stability. Requests define the minimum resources a container needs, while limits define the maximum it can use. The scheduler uses requests to decide where to place pods. 

resources:
  requests:
    cpu: "250m"       # 0.25 CPU cores
    memory: "256Mi"   # 256 mebibytes
  limits:
    cpu: "1000m"      # 1 CPU core
    memory: "512Mi"   # 512 mebibytes

What happens:

  • CPU - Requests guarantee CPU time. Limits throttle CPU usage (container slows down)
  • Memory - Requests reserve memory. Exceeding limits causes container termination (OOMKilled)
Common Mistake: Not setting requests and limits leads to the "noisy neighbor" problem where one application can starve others of resources. Always set them, especially in shared clusters.

Quality of Service Classes

Kubernetes assigns QoS classes based on resource specifications:

  • Guaranteed - All containers have requests=limits for CPU and memory. Highest priority, last to be evicted
  • Burstable - At least one container has requests or limits. Medium priority
  • BestEffort - No requests or limits set. Lowest priority, first to be evicted under pressure

Horizontal Pod Autoscaler (HPA)

HPA automatically scales the number of pods based on observed metrics like CPU usage, memory, or custom metrics from your application. 

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-deployment
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80

This HPA maintains between 3 and 20 replicas, scaling when average CPU exceeds 70% or memory exceeds 80%. Requires metrics-server to be installed in the cluster.

Vertical Pod Autoscaler (VPA)

While HPA scales the number of pods, VPA adjusts CPU and memory requests/limits for containers. Useful when you don't know the right resource values upfront. 

apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: web-vpa
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-deployment
  updatePolicy:
    updateMode: "Auto"    # or "Off" for recommendations only

Jobs and CronJobs

Jobs create one or more pods and ensure they successfully complete. CronJobs create Jobs on a schedule.

One-time Job

apiVersion: batch/v1
kind: Job
metadata:
  name: data-migration
spec:
  template:
    spec:
      containers:
        - name: migrator
          image: myapp/migrator:1.0
          command: ["./migrate.sh"]
      restartPolicy: Never
  backoffLimit: 3    # Retry 3 times on failure

Scheduled CronJob

apiVersion: batch/v1
kind: CronJob
metadata:
  name: backup-job
spec:
  schedule: "0 2 * * *"    # Every day at 2 AM
  jobTemplate:
    spec:
      template:
        spec:
          containers:
            - name: backup
              image: myapp/backup:1.0
              command: ["./backup.sh"]
          restartPolicy: OnFailure
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 1

DaemonSets

DaemonSets ensure that all (or some) nodes run a copy of a pod. Useful for cluster-wide services like log collectors, monitoring agents, or network proxies. 

apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: fluentd
spec:
  selector:
    matchLabels:
      name: fluentd
  template:
    metadata:
      labels:
        name: fluentd
    spec:
      containers:
        - name: fluentd
          image: fluent/fluentd:v1.16
          volumeMounts:
            - name: varlog
              mountPath: /var/log
      volumes:
        - name: varlog
          hostPath:
            path: /var/log

Init Containers

Init containers run before app containers and must complete successfully before the main containers start. Use them for setup tasks like database migrations or configuration downloads. 

spec:
  initContainers:
    - name: init-db
      image: busybox:1.36
      command: ['sh', '-c', 'until nslookup database; do echo waiting for db; sleep 2; done']
    - name: migrate
      image: myapp/migrator:1.0
      command: ['./migrate.sh']
  containers:
    - name: app
      image: myapp:1.0

Namespaces and Multi-tenancy

Namespaces provide a way to divide cluster resources between multiple users or teams. They're virtual clusters within a physical cluster. 

# Create namespace
kubectl create namespace development
kubectl create namespace production

# Set resource quotas per namespace
apiVersion: v1
kind: ResourceQuota

  name: dev-quota
  namespace: development

    requests.cpu: "10"
    requests.memory: "20Gi"
    limits.cpu: "20"
    limits.memory: "40Gi"
    pods: "50"

RBAC (Role-Based Access Control)

RBAC controls who can do what in your cluster. It's essential for security in shared clusters.

Role and RoleBinding (namespace-scoped)

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: development
  name: pod-reader
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "watch", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: development
subjects:
  - kind: User
    name: jane
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io

ClusterRole and ClusterRoleBinding (cluster-wide)

apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: node-reader
rules:
  - apiGroups: [""]
    resources: ["nodes"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: read-nodes-global
subjects:
  - kind: Group
    name: devops
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: node-reader
  apiGroup: rbac.authorization.k8s.io

Custom Resource Definitions (CRDs)

CRDs extend Kubernetes API with your own resource types. Operators use CRDs to manage complex applications declaratively. 

apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: databases.example.com
spec:
  group: example.com
  versions:
    - name: v1
      served: true
      storage: true
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              properties:
                size:
                  type: string
                version:
                  type: string
  scope: Namespaced
  names:
    plural: databases
    singular: database
    kind: Database
Operators: Operators are controllers that watch CRDs and reconcile actual state with desired state. Popular examples include Prometheus Operator, Cert-Manager, and various database operators. They encode operational knowledge into software.

Managed Kubernetes in the Cloud with Terraform

While learning Kubernetes locally is valuable, production workloads typically run on managed Kubernetes services from cloud providers. These services handle control plane management, upgrades, and integration with cloud services. Terraform lets you define cloud infrastructure as code, making deployments reproducible and version-controlled.

Why Managed Kubernetes?

  • No control plane management - Cloud provider handles API server, etcd backups, and upgrades
  • High availability - Control plane runs across multiple zones automatically
  • Cloud integration - Seamless integration with load balancers, storage, and IAM
  • Automatic security patches - Providers handle security updates for control plane
  • Scaling - Easy to add or remove worker nodes

terraform {
  required_version = ">= 1.0"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

  region = var.aws_region
}

# Basic VPC for the cluster

  source  = "terraform-aws-modules/vpc/aws"
  version = "5.1.0"

  name = "${var.cluster_name}-vpc"
  cidr = "10.0.0.0/16"

  azs             = ["${var.aws_region}a", "${var.aws_region}b"]
  private_subnets = ["10.0.1.0/24", "10.0.2.0/24"]
  public_subnets  = ["10.0.101.0/24", "10.0.102.0/24"]

  enable_nat_gateway   = true
  single_nat_gateway   = true
  enable_dns_hostnames = true
}

# EKS control plane + managed node group
module "eks" {
  source  = "terraform-aws-modules/eks/aws"
  version = "19.16.0"

  cluster_name    = var.cluster_name
  cluster_version = "1.28"

  vpc_id     = module.vpc.vpc_id
  subnet_ids = module.vpc.private_subnets

  eks_managed_node_groups = {
    default = {
      desired_size = 2
      min_size     = 1
      max_size     = 4

      instance_types = ["t3.medium"]
      capacity_type  = "ON_DEMAND"
    }
  }
}

# Optional: configure kubectl after apply
resource "null_resource" "kubectl_config" {
  depends_on = [module.eks]

  provisioner "local-exec" {
    command = "aws eks update-kubeconfig --region ${var.aws_region} --name ${var.cluster_name}"
  }
}

Helm: The Kubernetes Package Manager

Helm is a package manager for Kubernetes that simplifies deploying and managing applications. Think of it like apt, yum, or brew for Kubernetes. Instead of managing dozens of YAML files, Helm lets you install complete applications with a single command.

Why Use Helm?

  • Templating - Reuse configurations across environments with variables
  • Package management - Install complex applications with dependencies in one command
  • Version control - Track application versions and easily rollback
  • Release management - Manage multiple releases of the same application
  • Community charts - Thousands of pre-built charts for popular applications

Core Helm Concepts

TermDefinition
Chart A package of Kubernetes resources. Contains templates, default values, and metadata.
Release An instance of a chart running in a Kubernetes cluster. You can have multiple releases of the same chart.
Repository A collection of charts. Similar to package repositories in Linux distros.
Values Configuration parameters that customize a chart installation.

Helm Tip: Always use helm upgrade --install in automation. This command installs if the release doesn't exist, or upgrades if it does, making your deployments idempotent.

Helmfile: Managing Multiple Releases

For complex environments with many Helm releases, Helmfile provides declarative configuration:

# helmfile.yaml
repositories:
  - name: bitnami
    url: https://charts.bitnami.com/bitnami

releases:
  - name: postgresql
    namespace: database
    chart: bitnami/postgresql
    version: 12.1.0
    values:
      - auth:
          username: myapp
          database: myapp_db

  - name: redis
    namespace: cache
    chart: bitnami/redis
    version: 17.0.0

  - name: myapp
    namespace: default
    chart: ./charts/myapp
    values:
      - values-{{ .Environment.Name }}.yaml

# Deploy all releases
helmfile sync

# Update all releases
helmfile apply

Kubernetes Best Practices

Security

1. Use Namespaces for Isolation

Separate workloads by namespace to provide resource isolation, access control boundaries, and billing separation.

kubectl create namespace production
kubectl create namespace development
kubectl create namespace staging

2. Implement Network Policies

Default deny all traffic, then explicitly allow only what's needed.

# Default deny all ingress
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
spec:
  podSelector: {}
  policyTypes:
    - Ingress

3. Use RBAC Strictly

  • Follow principle of least privilege
  • Avoid using cluster-admin role
  • Create specific roles for each team or application
  • Use service accounts for applications, not user accounts

4. Secure Secrets

  • Never commit secrets to Git
  • Use external secret management (AWS Secrets Manager, HashiCorp Vault, Azure Key Vault)
  • Enable encryption at rest for etcd
  • Consider using Sealed Secrets or External Secrets Operator

5. Scan Images for Vulnerabilities

# Use Trivy for scanning
trivy image nginx:latest

# Integrate scanning in CI/CD
# Fail builds on high/critical vulnerabilities

6. Run Containers as Non-Root

securityContext:
  runAsNonRoot: true
  runAsUser: 1000
  allowPrivilegeEscalation: false
  capabilities:
    drop:
      - ALL
  readOnlyRootFilesystem: true

Reliability

1. Always Set Resource Requests and Limits

resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1000m"
    memory: "512Mi"

2. Use Liveness and Readiness Probes

Every container should have both probes configured appropriately.

3. Configure Pod Disruption Budgets

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: myapp-pdb
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: myapp

4. Use Pod Anti-Affinity for High Availability

affinity:
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchExpressions:
              - key: app
                operator: In
                values:
                  - myapp
          topologyKey: kubernetes.io/hostname

5. Implement Proper Logging

  • Log to stdout/stderr, not to files
  • Use structured logging (JSON)
  • Deploy a logging stack (ELK, Loki, or cloud-native solutions)
  • Include correlation IDs for distributed tracing

Operational Excellence

1. Use GitOps for Deployment

Store all Kubernetes manifests in Git and use tools like Flux or ArgoCD for automated deployments.

2. Tag Images Properly

  • Never use latest tag in production
  • Use semantic versioning or commit SHAs
  • Make images immutable
image: myapp:v1.2.3
# or
image: myapp:abc123def456

3. Label Everything

metadata:
  labels:
    app.kubernetes.io/name: myapp
    app.kubernetes.io/instance: myapp-prod
    app.kubernetes.io/version: "1.2.3"
    app.kubernetes.io/component: backend
    app.kubernetes.io/part-of: myplatform
    app.kubernetes.io/managed-by: helm
    environment: production
    team: platform

4. Implement Monitoring and Alerting

  • Deploy Prometheus for metrics
  • Use Grafana for visualization
  • Set up alerts for critical metrics
  • Monitor both application and cluster health

5. Regular Backup Strategy

  • Back up etcd regularly (managed clusters usually do this)
  • Use Velero for cluster backup and disaster recovery
  • Test your restore procedures
  • Back up persistent volumes

Cost Optimization

1. Right-Size Resources

  • Use VPA to find optimal resource settings
  • Monitor actual usage vs. requested resources
  • Remove unused resources

2. Use Cluster Autoscaler

Automatically adjust cluster size based on workload demands.

3. Consider Spot/Preemptible Instances

For non-critical workloads, use cheaper spot instances with appropriate tolerations.

4. Implement Resource Quotas

apiVersion: v1
kind: ResourceQuota
metadata:
  name: compute-quota
  namespace: development
spec:
  hard:
    requests.cpu: "10"
    requests.memory: "20Gi"
    limits.cpu: "20"
    limits.memory: "40Gi"
    pods: "50"

Development Workflow

1. Use Local Development Tools

  • Skaffold - Automates build, push, and deploy during development
  • Tilt - Manages your development workflow with live updates
  • Telepresence - Debug services locally while connected to remote cluster
  • kubectl port-forward - Quick access to services for debugging

2. Use ConfigMaps and Secrets for Configuration

Never hardcode configuration in images. Use ConfigMaps for non-sensitive data and Secrets for sensitive information.

3. Implement CI/CD Pipeline

# Example GitHub Actions workflow
name: Deploy to Kubernetes
on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      
      - name: Build and push image
        run: |
          docker build -t myapp:${{ github.sha }} .
          docker push myapp:${{ github.sha }}
      
      - name: Deploy to cluster
        run: |
          kubectl set image deployment/myapp myapp=myapp:${{ github.sha }}
          kubectl rollout status deployment/myapp

4. Use Helm for Complex Applications

Manage related resources as a single unit and enable easy configuration across environments.

5. Implement Health Checks Properly

  • Readiness probe - Is the app ready to serve traffic?
  • Liveness probe - Is the app still running?
  • Startup probe - Has the app finished starting up? (for slow-starting apps)
Golden Rule: Everything in Kubernetes should be declarative and version-controlled. If you're running imperative kubectl commands in production (except for debugging), you're doing it wrong. Use GitOps principles where your Git repository is the single source of truth.

Troubleshooting Guide

Kubernetes troubleshooting follows a systematic approach. Start from the top (is the cluster healthy?) and work down to the specific component having issues.

General Troubleshooting Workflow

1

Check Cluster Health

kubectl cluster-info
kubectl get nodes
kubectl get componentstatuses  # Deprecated but still useful
kubectl top nodes               # Resource usage
2

Check Pod Status

kubectl get pods
kubectl get pods -o wide        # Shows node and IP
kubectl describe pod 
kubectl get events --sort-by=.metadata.creationTimestamp
3

Check Logs

kubectl logs 
kubectl logs  -c 
kubectl logs  --previous    # Logs from crashed container
kubectl logs -f             # Follow logs
4

Interactive Debugging

kubectl exec -it  -- /bin/sh
kubectl run debug --image=busybox:1.36 --rm -it -- /bin/sh
kubectl debug  -it --image=busybox:1.36

Common Issues and Solutions

Pod Stuck in Pending State

Symptoms: Pod never starts, stays in Pending status

Common Causes:

  • Insufficient cluster resources (CPU/Memory)
  • No nodes match pod's node selector or affinity rules
  • PersistentVolumeClaim not bound

Debug Commands:

kubectl describe pod 
# Look for "Events" section at bottom
# Check for messages like "Insufficient cpu" or "No nodes available"

kubectl get pvc
# Check if PVC is "Bound"

kubectl get nodes -o json | jq '.items[].status.allocatable'
# Check available resources per node

Pod Stuck in ImagePullBackOff or ErrImagePull

Symptoms: Pod can't pull the container image

Common Causes:

  • Image name is incorrect or doesn't exist
  • Registry authentication failed
  • Network issues accessing registry

Solutions:

# Verify image exists
docker pull 

# Check imagePullSecrets
kubectl get secrets
kubectl describe secret 

# Create registry secret
kubectl create secret docker-registry regcred \
  --docker-server= \
  --docker-username= \
  --docker-password=

# Add to pod spec
spec:
  imagePullSecrets:
    - name: regcred

CrashLoopBackOff

Symptoms: Pod starts then immediately crashes, repeatedly

Common Causes:

  • Application error or crash on startup
  • Missing configuration or environment variables
  • Failed liveness probe
  • Insufficient permissions

Debug:

# Check current logs
kubectl logs 

# Check previous container logs (from crashed instance)
kubectl logs  --previous

# Describe pod for events
kubectl describe pod 

# Check if it's a liveness probe issue
# Look for "Liveness probe failed" in events

Service Not Accessible

Symptoms: Can't reach application through Service

Debug Steps:

# Check service exists and has endpoints
kubectl get svc
kubectl get endpoints 

# If no endpoints, check if pods have matching labels
kubectl get pods --show-labels
kubectl describe svc 
# Compare "Selector" with pod labels

# Test from inside cluster
kubectl run test --image=busybox:1.36 --rm -it -- /bin/sh
wget -O- :

# Check service type and external access
kubectl get svc 
# For LoadBalancer, check if EXTERNAL-IP is assigned

# Check network policies
kubectl get networkpolicies

Ingress Not Working

Common Issues:

# Verify Ingress Controller is running
kubectl get pods -n ingress-nginx

# Check Ingress resource
kubectl get ingress
kubectl describe ingress 

# Verify backend service exists and has endpoints
kubectl get svc 
kubectl get endpoints 

# Check Ingress Controller logs
kubectl logs -n ingress-nginx 

# Verify DNS points to Ingress Controller's external IP
kubectl get svc -n ingress-nginx

Persistent Volume Claims Not Binding

Debug:

# Check PVC status
kubectl get pvc
kubectl describe pvc 

# Check if matching PV exists
kubectl get pv

# Check StorageClass
kubectl get storageclass
kubectl describe storageclass 

# For dynamic provisioning, check provisioner logs
kubectl logs -n kube-system -l app=

High Resource Usage / OOMKilled

Symptoms: Pods getting killed due to memory limits

# Check resource usage
kubectl top pods
kubectl top nodes

# Check if pod was OOMKilled
kubectl describe pod 
# Look for "Last State: Terminated, Reason: OOMKilled"

# Review resource limits
kubectl get pod  -o yaml | grep -A 10 resources

# Increase memory limits if legitimate usage
# Or investigate memory leak in application
