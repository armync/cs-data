Networking in Multi-Node Kubernetes Cluster: The Role of Calico

In a multi-node Kubernetes cluster, networking is a crucial component that ensures smooth communication between pods, nodes, and external clients. Without proper networking setup, pods running on different nodes with the same IP address cannot connect, causing disruptions in the cluster. In this article, we will explore how Kubernetes networking works, why overlay networks and CNI (Container Network Interface) are necessary, and how to implement these using Calico.

The Networking Challenge: Pods with the Same IP on Different Nodes

By default, Kubernetes assigns a unique IP address to each pod. However, in a multi-node cluster, you might run into a problem: pods running on different nodes may end up with the same IP address. This is due to the way Kubernetes allocates IP addresses across nodes, which can lead to communication failures between pods on different nodes.
This issue has been faced while launching the pods in a Multi Node Cluster in this article.

To solve this, we need a network overlay, which allows the pods on different nodes to communicate seamlessly. The overlay network creates a virtual network that abstracts the underlying physical infrastructure. Kubernetes provides flexibility in choosing networking solutions, and one of the most popular choices is Calico, which implements the CNI (Container Network Interface) standard.

Why Calico?

Calico is a powerful networking and network security solution that is widely used in Kubernetes environments. It provides the following benefits:

  • Pod-to-Pod Communication: Calico manages IP addresses and network routing across nodes, allowing pods to connect even if they are on different nodes.
  • Network Policies: Calico allows you to define fine-grained network policies, ensuring secure and controlled communication.
  • CNI Compatibility: Calico works as a CNI plugin, providing the flexibility to integrate with other networking solutions and maintain scalability.

In this article, we will walk through the process of setting up Calico as the networking solution in a multi-node Kubernetes cluster.

Setting Up the Cluster

Before setting up Calico, ensure that your multi-node cluster is up and running. For this example, we assume you have a Kubernetes cluster with at least two nodes. Here’s how to proceed:

Delete All Pods and Deployments: Before installing Calico, you should clear the cluster of any existing pods or deployments:

kubectl delete all --all

Install Calico

Now, let’s install Calico on the cluster to enable networking.

Step 1: Download the Calico Manifest

Calico provides a YAML manifest file that contains all the necessary configurations to deploy it in Kubernetes. You can download the latest version of the manifest using the following command:

curl -O https://raw.githubusercontent.com/projectcalico/calico/master/manifests/calico.yaml

Step 2: Apply the Manifest

Once you’ve downloaded the manifest, apply it to your Kubernetes cluster:

kubectl apply -f calico.yaml

This will deploy Calico across all nodes in the cluster, and you’ll see Calico pods being launched.

Auto-Detection of Network Interfaces

One of the challenges in a multi-node Kubernetes cluster is dealing with multiple network interfaces on each node. By default, Calico uses the first detected network interface. However, in some cases, this detection may not work correctly due to the presence of multiple network cards.

To configure Calico to use a specific network card:

  1. Locate the calico.yaml file.
  2. Search for autodetect in the file.
  3. If the auto-detection method is not detecting the correct network card, modify it to specify the correct interface name.

Added below script:

- name: IP_AUTODETECTION_METHOD
  value: "interface=eth0"

After making the necessary changes, apply the updated YAML file again:

kubectl apply -f calico.yaml

Verifying the Calico Pods

Once Calico is installed, Kubernetes will create a set of Calico pods. The number of Calico pods should be equal to the number of nodes in the cluster, ensuring that each node is properly configured for networking.

You can check the status of the pods using the following command:

kubectl get pods -n kube-system

Bird Daemon

Calico uses the Bird program behind the scenes to handle BGP (Border Gateway Protocol) for routing between pods across different nodes. Bird helps in advertising routes to other nodes, which is essential for network communication between pods.

You can check the Bird daemon logs to ensure that it is functioning properly:

kubectl logs <bird-pod-name> -n calico-system

Create a Deployment with Multiple Replicas

To test the networking setup, we can create a deployment with multiple replicas. This will ensure that pods across different nodes can communicate with each other.

For example, let’s create a deployment with 5 replicas of a simple httpd pod:

kubectl create deployment myd --image=httpd --replicas=5

You can verify that all the pods are launched with different IP addresses using the following command:

kubectl get pods -o wide

If everything is set up correctly, each pod should have a unique IP address.

Summary

Networking in a multi-node Kubernetes cluster is essential for efficient communication between pods, services, and external clients. In this article, we discussed how Calico, as a CNI plugin, can help solve networking challenges in multi-node clusters. By using Calico, you can ensure that your pods across different nodes can communicate with each other without IP conflicts.

In addition to networking, tools like kube-proxy ensure proper traffic routing, allowing for efficient service exposure and communication. Whether you’re adding more nodes or scaling your applications, Calico provides the robust networking needed for large, distributed Kubernetes environments.
