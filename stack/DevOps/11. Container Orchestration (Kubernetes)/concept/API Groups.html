Ever seen a Kubernetes YAML and wondered what apps/v1 or rbac.authorization.k8s.io/v1 really mean? You're not alone. Kubernetes organizes its chaos with API groups and understanding them makes everything else easier.

What Are Kubernetes API Groups?

Kubernetes has many types of resources (like pods, deployments, services, nodes, etc.). These are organized into logical groups called API Groups.

It's like putting different topics into folders:

  • Cars (Pods, Services) → core group
  • Infrastructure (Nodes, PersistentVolumes) → core
  • User controls (Roles, RBAC) → rbac.authorization.k8s.io
  • Custom features (Ingress, Deployments) → apps, networking.k8s.io

Each API resource belongs to a specific group and version. So when you define things in YAML, like:

apiVersion: apps/v1
kind: Deployment

You're saying:

  • Group = apps
  • Version = v1

Types of API Groups in Kubernetes

1. Core Group (aka Legacy)

  • These have no group name in apiVersion, just like: apiVersion: v1
  • Includes: Pod, Service, Node, Namespace, Secret, ConfigMap, etc.

These are fundamental building blocks, so they're in the core group.

2. Named API Groups

These have a group name and are used for modular, newer, or extended resources.

a. apps

Resources:

  • Deployment, DaemonSet, StatefulSet, ReplicaSet
  • apiVersion: apps/v1

b. batch

Resources:

  • Job, CronJob
  • apiVersion: batch/v1

c. rbac.authorization.k8s.io

Resources:

  • Role, ClusterRole, RoleBinding, ClusterRoleBinding
  • apiVersion: rbac.authorization.k8s.io/v1

d. networking.k8s.io

Resources:

  • Ingress, NetworkPolicy
  • apiVersion: networking.k8s.io/v1

e. policy

Resources:

  • PodDisruptionBudget
  • apiVersion: policy/v1

f. autoscaling

Resources:

  • HorizontalPodAutoscaler
  • apiVersion: autoscaling/v2 (or v1)

g. certificates.k8s.io

Resources:

  • CertificateSigningRequest
  • apiVersion: certificates.k8s.io/v1

Directory Style Mental Model

apiVersion: <group>/<version>
kind: <resource>

Imagine the structure like:

├── core (v1)
│   ├── Pod
│   ├── Service
│
├── apps (v1)
│   ├── Deployment
│   ├── StatefulSet
│
├── batch (v1)
│   ├── Job
│   ├── CronJob
│
├── rbac.authorization.k8s.io (v1)
│   ├── Role
│   ├── ClusterRole
│
├── certificates.k8s.io (v1)
│   ├── CertificateSigningRequest

Why Should You Care?

Because:

  • RBAC applies permissions per API group.
  • Knowing API groups helps with creating correct YAML files.
  • Debugging: Errors often say "resource not found in group X".
  • kubectl api-resources shows you resources and their groups.

Try this: See All API Resources and Groups

kubectl api-resources

Output looks like:

NAME               SHORTNAMES   APIGROUP                       NAMESPACED   KIND
pods               po                                         true         Pod
deployments        deploy       apps                          true         Deployment
roles                           rbac.authorization.k8s.io     true         Role

You'll get a full list of resources, what group they're in, and if they're namespaced or not.
