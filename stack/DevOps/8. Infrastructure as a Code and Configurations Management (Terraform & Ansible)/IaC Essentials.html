Infrastructure as Code Essential Guide

What is Infrastructure as Code (IaC)?

Infrastructure as Code (IaC) is the practice of managing and provisioning infrastructure through machine-readable definition files rather than physical hardware configuration or interactive configuration tools. Instead of manually clicking through cloud consoles or running ad-hoc commands, you write code that declares what your infrastructure should look like.

Key Principle: Your infrastructure is defined in code files that can be versioned, reviewed, tested, and automated just like application code.

Why Use Infrastructure as Code?

Consistency

Eliminate configuration drift and "works on my machine" issues. The same code produces identical infrastructure every time.

Repeatability

Deploy the same infrastructure across multiple environments (dev, staging, prod) with confidence.

Versioning

Track every change to your infrastructure in Git. Roll back to previous versions if needed.

Collaboration

Use pull requests, code reviews, and team workflows for infrastructure changes.

Speed

Provision entire environments in minutes instead of hours or days of manual work.

Documentation

Your code serves as living documentation of your infrastructure setup.

IaC vs Traditional Infrastructure Management

Aspect Traditional (Manual) Infrastructure as Code
Provisioning Click through consoles, run manual commands Run a single command to apply code
Documentation Separate docs that become outdated Code is the documentation
Changes High risk, difficult to track Versioned, reviewable, auditable
Disaster Recovery Manual rebuild, prone to errors Re-run code to recreate infrastructure
Scaling Time-consuming and error-prone Modify parameters and reapply

Introduction to Terraform Basics

Terraform is an open-source Infrastructure as Code tool created by HashiCorp. It uses a declarative language called HCL (HashiCorp Configuration Language) to define infrastructure resources across multiple cloud providers and services.

Key Concepts

1. Providers

Providers are plugins that enable Terraform to interact with cloud platforms, SaaS providers, and other APIs. Each provider adds a set of resource types and data sources that Terraform can manage.

terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = "us-east-1"
}
Popular Providers: AWS, Azure, Google Cloud, Kubernetes, Docker, GitHub, Datadog, and hundreds more.

2. Resources

Resources are the most important element in Terraform. Each resource block describes one or more infrastructure objects, such as virtual machines, storage buckets, or networking components.

resource "aws_instance" "web_server" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"

  tags = {
    Name = "WebServer"
    Environment = "Production"
  }
}

Syntax: resource "TYPE" "NAME"

  • TYPE: Resource type from the provider (e.g., aws_instance)
  • NAME: Local name you choose to reference this resource

3. Variables

Variables make your configurations flexible and reusable. They allow you to parameterize your code without hardcoding values.

variable "instance_type" {
  description = "EC2 instance type"
  type        = string
  default     = "t2.micro"
}

variable "environment" {
  description = "Environment name"
  type        = string
}

variable "enable_monitoring" {
  description = "Enable detailed monitoring"
  type        = bool
  default     = false
}

resource "aws_instance" "server" {
  instance_type = var.instance_type

  tags = {
    Environment = var.environment
  }
}

4. Outputs

Outputs extract information about your infrastructure after it's created. They're useful for displaying important values or passing data between modules.

output "instance_ip" {
  description = "Public IP of the EC2 instance"
  value       = aws_instance.web_server.public_ip
}

output "instance_id" {
  description = "ID of the EC2 instance"
  value       = aws_instance.web_server.id
  sensitive   = false
}

5. State Files

Terraform stores information about your managed infrastructure in a state file (terraform.tfstate). This state is used to map real-world resources to your configuration and track metadata.

Critical: State files contain sensitive information and should never be committed to version control. Use remote state storage for production environments.

6. Data Sources

Data sources allow Terraform to fetch information from existing resources not managed by your current configuration.

data "aws_ami" "ubuntu" {
  most_recent = true
  owners      = ["099720109477"] # Canonical

  filter {
    name   = "name"
    values = ["ubuntu/images/hvm-ssd/ubuntu-focal-20.04-amd64-server-*"]
  }
}

resource "aws_instance" "web" {
  ami           = data.aws_ami.ubuntu.id
  instance_type = "t2.micro"
}

7. Local Values

Locals are named values that you can reference multiple times within a module. They help reduce repetition and make your code more maintainable.

locals {
  common_tags = {
    Project     = "MyApp"
    ManagedBy   = "Terraform"
    Environment = var.environment
  }

  instance_name = "${var.project_name}-${var.environment}-instance"
}

resource "aws_instance" "app" {
  ami           = var.ami_id
  instance_type = var.instance_type

  tags = merge(
    local.common_tags,
    {
      Name = local.instance_name
    }
  )
}

How Terraform Interacts with Cloud Platforms

1

Authentication

Terraform authenticates with the cloud provider using credentials (API keys, service accounts, etc.)

2

API Calls

Providers translate your HCL configuration into API calls to the cloud platform

3

State Tracking

Terraform tracks resources in the state file, mapping configuration to real infrastructure

4

Drift Detection

On subsequent runs, Terraform compares desired state (code) with actual state (cloud resources)

Write and Apply Your First Terraform Configuration

Let's create a simple but practical example: provisioning an AWS S3 bucket with versioning and encryption.

Step 1: Create Project Structure

my-first-terraform/
 main.tf          # Main configuration
 variables.tf     # Variable definitions
 outputs.tf       # Output values
 terraform.tfvars # Variable values (don't commit secrets!)

Step 2: Write Configuration Files

main.tf

terraform {
  required_version = ">= 1.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = var.aws_region
}

resource "aws_s3_bucket" "my_bucket" {
  bucket = "${var.project_name}-${var.environment}-bucket"

  tags = {
    Name        = "My First Terraform Bucket"
    Environment = var.environment
    ManagedBy   = "Terraform"
  }
}

resource "aws_s3_bucket_versioning" "my_bucket_versioning" {
  bucket = aws_s3_bucket.my_bucket.id

  versioning_configuration {
    status = "Enabled"
  }
}

resource "aws_s3_bucket_server_side_encryption_configuration" "my_bucket_encryption" {
  bucket = aws_s3_bucket.my_bucket.id

  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm = "AES256"
    }
  }
}

variables.tf

variable "aws_region" {
  description = "AWS region to deploy resources"
  type        = string
  default     = "us-east-1"
}

variable "project_name" {
  description = "Project name for resource naming"
  type        = string
}

variable "environment" {
  description = "Environment (dev, staging, prod)"
  type        = string

  validation {
    condition     = contains(["dev", "staging", "prod"], var.environment)
    error_message = "Environment must be dev, staging, or prod."
  }
}

outputs.tf

output "bucket_name" {
  description = "Name of the S3 bucket"
  value       = aws_s3_bucket.my_bucket.id
}

output "bucket_arn" {
  description = "ARN of the S3 bucket"
  value       = aws_s3_bucket.my_bucket.arn
}

output "bucket_region" {
  description = "Region of the S3 bucket"
  value       = aws_s3_bucket.my_bucket.region
}

terraform.tfvars

project_name = "myapp"
environment  = "dev"
aws_region   = "us-west-2"

Step 3: Initialize Terraform

terraform init
This command downloads the AWS provider plugin and prepares your working directory.

Step 4: Validate Configuration

terraform validate

Step 5: Plan Changes

terraform plan

The plan output shows:

  • Resources to be created (+)
  • Resources to be modified (~)
  • Resources to be destroyed (-)

Step 6: Apply Configuration

terraform apply

terraform apply -auto-approve
After applying, Terraform creates a terraform.tfstate file that tracks your infrastructure.

Step 7: Verify Outputs

terraform output

terraform output bucket_name

Step 8: Make Changes

Edit your configuration to add a lifecycle rule:

resource "aws_s3_bucket_lifecycle_configuration" "my_bucket_lifecycle" {
  bucket = aws_s3_bucket.my_bucket.id

  rule {
    id     = "delete-old-versions"
    status = "Enabled"

    noncurrent_version_expiration {
      noncurrent_days = 90
    }
  }
}

terraform plan
terraform apply

Step 9: Destroy Resources

terraform destroy

terraform destroy -target=aws_s3_bucket.my_bucket

Storing State Securely

The state file is Terraform's source of truth. For production use, always use remote state storage:

S3 Backend (AWS)

terraform {
  backend "s3" {
    bucket         = "my-terraform-state-bucket"
    key            = "project/terraform.tfstate"
    region         = "us-east-1"
    encrypt        = true
    dynamodb_table = "terraform-state-lock"
  }
}

Azure Storage Backend

terraform {
  backend "azurerm" {
    resource_group_name  = "tfstate-rg"
    storage_account_name = "tfstateaccount"
    container_name       = "tfstate"
    key                  = "prod.terraform.tfstate"
  }
}
State File Security Best Practices:
  • Enable encryption at rest
  • Use state locking to prevent concurrent modifications
  • Restrict access with IAM policies
  • Enable versioning for state file backups
  • Never commit state files to Git

Modules for Reusable Code

How this maps to Ansible (Roles)

If you come from Ansible, think of Terraform modules like Ansible Roles: both package reusable logic plus inputs (variables) and outputs. You call Terraform modules with inputs and read outputs, similar to using role vars and role defaults in Ansible. Modules = reusable building blocks; Roles = reusable automation units.

- hosts: web
  roles:
    - role: nginx
      vars:
        listen_port: 80

module "vpc" {
  source = "./modules/vpc"
  cidr   = "10.0.0.0/16"
}

Modules are containers for multiple resources that are used together. They enable code reuse and organization.

Module Structure

modules/
 vpc/
     main.tf
     variables.tf
     outputs.tf
     README.md

Creating a Module (modules/vpc/main.tf)

resource "aws_vpc" "main" {
  cidr_block           = var.vpc_cidr
  enable_dns_hostnames = true
  enable_dns_support   = true

  tags = merge(
    var.tags,
    {
      Name = var.vpc_name
    }
  )
}

resource "aws_subnet" "public" {
  count             = length(var.public_subnet_cidrs)
  vpc_id            = aws_vpc.main.id
  cidr_block        = var.public_subnet_cidrs[count.index]
  availability_zone = var.availability_zones[count.index]

  map_public_ip_on_launch = true

  tags = merge(
    var.tags,
    {
      Name = "${var.vpc_name}-public-${count.index + 1}"
      Type = "Public"
    }
  )
}

Using a Module (root main.tf)

module "vpc" {
  source = "./modules/vpc"

  vpc_name            = "production-vpc"
  vpc_cidr            = "10.0.0.0/16"
  public_subnet_cidrs = ["10.0.1.0/24", "10.0.2.0/24"]
  availability_zones  = ["us-east-1a", "us-east-1b"]

  tags = {
    Environment = "Production"
    Project     = "MyApp"
  }
}

output "vpc_id" {
  value = module.vpc.vpc_id
}

Best Practices Summary

Structure

Organize code into modules. Keep root configs simple and delegate to modules.

State

Always use remote state with locking for production. Enable versioning and encryption.

Secrets

Never hardcode secrets. Use variables, environment variables, or secret management tools.

Version Control

Commit .tf files to Git. Add .gitignore for state files, .terraform/, and *.tfvars with secrets.

Testing

Always run terraform plan before apply. Use terraform validate for syntax checks.

Documentation

Use descriptions in variables and outputs. Include README.md in modules.

Advanced Terraform Topics

Terraform State and State Drift

State is Terraform's record of what infrastructure exists. State drift occurs when the real infrastructure no longer matches what's recorded in the state file.

Causes of State Drift

  • Manual changes made through cloud console
  • Resources modified by other tools or scripts
  • Auto-scaling or self-healing mechanisms
  • Resources deleted outside of Terraform

Detecting and Handling Drift

terraform refresh

terraform plan

terraform state list
terraform state show aws_instance.web_server
Note: terraform refresh is deprecated. Use terraform apply -refresh-only instead.

Importing Existing Resources

terraform import aws_instance.web_server i-1234567890abcdef0

resource "aws_instance" "web_server" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"
}

Configuration Drift Detection

Configuration drift happens when infrastructure diverges from its defined configuration over time.

Prevention Strategies

1

Scheduled Drift Detection

Run terraform plan regularly in CI/CD to detect unauthorized changes

2

Policy as Code

Use Sentinel or OPA to enforce policies and prevent manual changes

3

Lifecycle Policies

Use lifecycle blocks to ignore expected changes from auto-scaling or external updates

resource "aws_instance" "web" {
  ami           = var.ami_id
  instance_type = var.instance_type

  lifecycle {
    ignore_changes = [
      tags["LastScanned"],
      tags["Backup"]
    ]

    prevent_destroy = true

    create_before_destroy = true
  }
}

Idempotence in Terraform

Idempotence means running the same operation multiple times produces the same result. Terraform is inherently idempotent.

Idempotent Behavior: Running terraform apply multiple times with the same configuration results in no changes after the first apply. 
$ terraform apply

$ terraform apply

$ terraform apply
$ terraform apply
$ terraform apply

When Idempotence Can Break

resource "aws_instance" "web" {
  ami           = var.ami_id
  instance_type = "t2.micro"

  tags = {
    Created = timestamp()  # Changes every apply!
  }
}

resource "aws_instance" "web" {
  ami           = var.ami_id
  instance_type = "t2.micro"

  tags = {
    Created = "2025-01-15"  # Static, won't change
  }
}

Variable Precedence

How Terraform Resolves Variable Values

When multiple sources provide the same variable, Terraform uses this order (highest to lowest priority):

Priority Method Example Use Case
1 (Highest) Command-line flags -var="instance_type=t3.large" One-off overrides
2 Variable files (-var-file) -var-file="prod.tfvars" Environment-specific configs
3 terraform.tfvars instance_type = "t3.medium" Default values for project
4 *.auto.tfvars (alphabetical) common.auto.tfvars Auto-loaded configs
5 Environment variables TF_VAR_instance_type=t3.small CI/CD secrets
6 (Lowest) Default in variables.tf default = "t3.micro" Fallback values

Example:

# variables.tf
variable "instance_type" {
  default = "t3.micro"  # Priority 6
}

# terraform.tfvars
instance_type = "t3.small"  # Priority 3

# Run command:
$ export TF_VAR_instance_type=t3.medium  # Priority 5
$ terraform apply -var="instance_type=t3.large"  # Priority 1

# Result: Uses t3.large (highest priority wins!)

Secrets Management

Never store secrets in Terraform code or state files in plain text. Use secure secret management solutions.

Method 1: Environment Variables

export TF_VAR_db_password="super-secret-password"

variable "db_password" {
  type      = string
  sensitive = true
}

resource "aws_db_instance" "main" {
  password = var.db_password
}

Method 2: AWS Secrets Manager

data "aws_secretsmanager_secret_version" "db_password" {
  secret_id = "prod/database/password"
}

resource "aws_db_instance" "main" {
  password = jsondecode(data.aws_secretsmanager_secret_version.db_password.secret_string)["password"]

}

Method 3: HashiCorp Vault

provider "vault" {
  address = "https://vault.example.com"
}

data "vault_generic_secret" "db_creds" {
  path = "secret/database/prod"
}

resource "aws_db_instance" "main" {
  username = data.vault_generic_secret.db_creds.data["username"]
  password = data.vault_generic_secret.db_creds.data["password"]
}

Method 4: Terraform Cloud/Enterprise


variable "api_key" {
  type      = string
  sensitive = true
}

resource "datadog_monitor" "api" {

  depends_on = [var.api_key]
}
Secret Management Best Practices:
  • Mark variables as sensitive = true
  • Use external secret stores (Vault, AWS Secrets Manager)
  • Rotate secrets regularly
  • Encrypt state files at rest
  • Restrict access to state with IAM policies
  • Never commit .tfvars files with secrets to Git

When to Use Each

Variables

Use when: You need configurable inputs that change between environments or deployments

Example: Instance types, region names, environment names

Locals

Use when: You need to compute values or avoid repetition within a module

Example: Combined strings, common tags, conditional logic

Outputs

Use when: You need to export information for other modules or external systems

Example: IP addresses, resource IDs, connection strings

Resource References and Dependencies

Implicit Dependencies

resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}

resource "aws_subnet" "public" {
  vpc_id     = aws_vpc.main.id  # Implicit dependency
  cidr_block = "10.0.1.0/24"
}

Explicit Dependencies

resource "aws_instance" "app" {
  ami           = var.ami_id
  instance_type = "t3.micro"

  depends_on = [
    aws_iam_role_policy.app_policy,
    aws_security_group.app_sg
  ]
}

Count and For_Each

resource "aws_instance" "web" {
  count         = 3
  ami           = var.ami_id
  instance_type = "t3.micro"

  tags = {
    Name = "web-server-${count.index + 1}"
  }
}

resource "aws_instance" "servers" {
  for_each = {
    web = "t3.small"
    api = "t3.medium"
    db  = "t3.large"
  }

  ami           = var.ami_id
  instance_type = each.value

  tags = {
    Name = "${each.key}-server"
    Type = each.key
  }
}
Feature Count For_Each
Input Type Number Map or Set
Reference Style By index: resource[0] By key: resource["name"]
Reordering Impact Changes indices, may recreate resources Keys stay stable, safer for changes
Best For Simple lists, numbered resources Named resources, dynamic sets

Complete Example: Multi-Tier Application


locals {
  environment = "production"
  project     = "myapp"

  common_tags = {
    Project     = local.project
    Environment = local.environment
    ManagedBy   = "Terraform"
  }
}

module "vpc" {
  source = "./modules/vpc"

  vpc_name = "${local.project}-${local.environment}"
  vpc_cidr = var.vpc_cidr

  availability_zones  = var.availability_zones
  public_subnet_cidrs = var.public_subnet_cidrs
  private_subnet_cidrs = var.private_subnet_cidrs

  tags = local.common_tags
}

module "database" {
  source = "./modules/rds"

  db_name             = var.db_name
  db_instance_class   = var.db_instance_class
  allocated_storage   = var.db_storage

  subnet_ids          = module.vpc.database_subnet_ids
  vpc_id              = module.vpc.vpc_id

  tags = local.common_tags
}

module "application" {
  source = "./modules/ecs-app"

  app_name         = local.project
  environment      = local.environment

  vpc_id           = module.vpc.vpc_id
  private_subnets  = module.vpc.private_subnet_ids
  public_subnets   = module.vpc.public_subnet_ids

  database_url     = module.database.connection_string

  desired_count    = var.app_desired_count
  container_image  = var.container_image

  tags = local.common_tags
}

output "application_url" {
  description = "URL of the application load balancer"
  value       = module.application.alb_dns_name
}

output "vpc_id" {
  description = "ID of the VPC"
  value       = module.vpc.vpc_id
}

output "database_endpoint" {
  description = "Database endpoint"
  value       = module.database.endpoint
  sensitive   = true
}
