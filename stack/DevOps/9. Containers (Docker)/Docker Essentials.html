Docker Essential Guide

Introduction to Containers and Docker

Containers package an application and its runtime dependencies into a single, portable unit. They are lighter than virtual machines because they share the host OS kernel while isolating processes, filesystems, networking, and resources.

Consistency

Run the same artifact across dev, CI, and prod.

Speed

Faster startup and lower overhead than VMs.

Portability

Works on any OCI-compatible runtime.

Isolation

Sandboxed processes and filesystems.

Essential Commands (Step-by-Step)

1

Discover

See your environment, images, and containers.

docker version                # client/server versions
docker info                   # host, storage driver, CPUs, etc.
docker images                 # local image cache
docker ps                     # running containers
docker ps -a                  # all containers (incl. exited)
2

Build

Create an image from a Dockerfile (with useful variants).

docker build -t myimg:1.0 .               # tag image
docker build --no-cache -t myimg:1.0 .    # ignore build cache
docker build -f Dockerfile.ci -t myimg:ci . # use alternate Dockerfile
3

Run

Start containers; map ports, mount volumes, and set name/env.

docker run -it --rm alpine:3.20 sh        # -i interactive, -t TTY, --rm auto-clean on exit
docker run -d --name web -p 8080:80 nginx:alpine  # -d detached, -p host:container port
docker run -d --name app -e NODE_ENV=prod -v appdata:/var/lib/app myimg:1.0  # -v named volume
4

Interact

Operate containers without re-running them.

docker start <container>                  # start stopped container
docker stop <container>                   # send SIGTERM then SIGKILL
docker restart <container>
docker exec -it <container> sh            # run a command inside
docker logs -f <container>                # follow logs
5

Inspect

Query details for debugging and automation.

docker inspect <container-or-image>       # JSON metadata
docker stats                              # live resource usage
docker cp <container>:/path/in /host/path # copy out
docker cp /host/path <container>:/path/in  # copy in
6

Images & Registry

Pull/push images and manage local cache.

docker pull nginx:alpine
docker tag myimg:1.0 myrepo/myimg:1.0
docker push myrepo/myimg:1.0
docker rmi <image-id>                      # remove image by id or name:tag
docker login; docker logout
docker search nginx
7

Networks & Volumes

Create and inspect connectivity and storage.

docker network create appnet
docker network ls; docker network inspect appnet
docker network connect appnet web          # attach container to network

docker volume create appdata
docker volume ls; docker volume inspect appdata
docker volume rm appdata
8

Clean Up

Remove unused resources safely or aggressively.

docker system prune              # prompt by default (containers, networks, build cache)
docker container prune           # remove stopped containers
docker image prune               # dangling/unused images
docker volume prune              # unused volumes
docker network prune             # unused networks
9

Swarm (Optional)

Swarm is Docker’s built‑in orchestrator. It lets you join multiple hosts into a cluster (a “swarm”), run services with a desired number of replicas, roll out updates, and get built‑in load balancing. You only need it for multi‑host or high availability; plain Docker and Compose don’t use Swarm.

docker swarm init
docker swarm join --token <token> <manager-ip>
docker node ls
docker service create --name web nginx:alpine
docker service ls
docker service scale web=3
docker service logs web
Tip: The steps above cover the everyday Docker flow plus optional Swarm. Compose builds on these without repeating them.

Images vs. Containers

Images are read-only templates built from a Dockerfile. A container is a running (or stopped) instance of an image with a writable layer on top.

Layers & Caching

  • Each RUN, COPY, and ADD creates a new layer.
  • Cache hits depend on the order of instructions and file changes.
  • Prefer small, stable base images (e.g., alpine, debian:stable-slim).

Pull by Tag vs. Digest

# pull by tag
docker pull nginx:1.27-alpine
# pull by digest (immutable)
docker pull nginx@sha256:<digest>

Dockerfile

Keep images minimal, deterministic, and reproducible. Use multi-stage builds and run as a non-root user when possible.

Minimal Node.js API (Multi-Stage)

# syntax=docker/dockerfile:1
ARG NODE_VERSION=22-alpine
FROM node:${NODE_VERSION} AS base
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production

FROM base AS build
RUN npm ci
COPY . .
RUN npm run build

FROM node:${NODE_VERSION} AS runtime
ENV NODE_ENV=production
WORKDIR /app
COPY --from=build /app/dist ./dist
COPY --from=base /app/node_modules ./node_modules
EXPOSE 3000
USER node
CMD ["node", "dist/index.js"]

RUNRuns a command while building the image. Each RUN adds a new layer.RUN apk add --no-cache curl

EXPOSELists the ports your container will use. It’s for documentation and doesn’t actually publish ports.EXPOSE 8080

Docker Compose

Compose defines and runs multi-container apps using a declarative compose.yaml. You describe services, networks, and volumes in one file, and the CLI creates them as a project.

Compose today: Use docker compose (Compose V2, built into Docker). In compose.yaml you usually omit version:. Use the old docker-compose CLI or add a version: only for legacy environments.

How Compose is structured

  • services: containers that make up your app (web, api, db).
  • networks: optional isolated networks for service-to-service traffic.
  • volumes: persistent data (named volumes) or bind mounts from the host.
  • project name: derived from folder by default; use -p to override.
  • env files: load .env automatically; you can also specify env_file:.
  • depends_on: controls start order; with healthchecks you can wait for healthy.
  • build: context, Dockerfile, target; great for dev flows.
  • ports: publish container ports; format host:container.
  • deploy: section is for Swarm/Kubernetes only; it’s ignored in plain Compose.

Web + API + Database

services:
  db:
    image: postgres:16
    environment:
      POSTGRES_DB: app
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
    volumes:
      - dbdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 10s
      timeout: 5s
      retries: 5

  api:
    build: ./api
    environment:
      DATABASE_URL: postgres://app:secret@db:5432/app
    depends_on:
      db:
        condition: service_healthy    # wait until db reports healthy
    ports:
      - "3000:3000"                   # expose API to host 3000

  web:
    build: ./web
    ports:
      - "8080:80"                     # map host 8080 to Nginx 80
    depends_on:
      - api                            # start web after api

volumes:
  dbdata:                               # named volume persists db data

Compose Commands (with quick comments)

docker compose up                # build (if needed) + start in foreground
docker compose up -d             # start detached
docker compose build             # (re)build services
docker compose ps                # list project containers
docker compose logs -f           # stream logs for all services
docker compose exec api sh       # open a shell inside the api container
docker compose down              # stop & remove containers, networks
# legacy alias (older environments):
# docker-compose up / down / ps / logs

Best Practices

Security

Run as non-root; minimize packages; scan images (Trivy, Docker Scout); consider distroless.

Performance

Leverage layer caching, .dockerignore, and multi-stage builds.

Observability

Logs to stdout/stderr; healthchecks; metrics.

Reproducibility

Pin base digests and tool versions; avoid mutable tags.

Troubleshooting

Gotcha: Containers exit when the PID 1 process ends. Ensure the main service stays in the foreground.
# inspect metadata
docker inspect <container-or-image>

# view verbose build output (BuildKit)
DOCKER_BUILDKIT=1 docker build . --target build --progress=plain
